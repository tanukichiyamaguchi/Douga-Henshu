`uv run python -m vfx <コマンド> --help` で引数の詳細が出る（tools/ で実行）。

## 26. 超解像（`upscale`） ◎

- 何をする: 小さい映像を、細部を補いながら大きくする
- 頼み方の例: 「この古い動画を大きくして、細かい所もはっきりさせて」
- 中身: auto（既定）: 3 倍以上は AI、それ未満は lanczos（試験の結果で決めた）。AI は Real-ESRGAN の realesr-general-x4v3 とノイズを残す版 realesr-general-wdn-x4v3（どちらも BSD-3-Clause、GitHub のリリース）の重みを --denoise の割合で混ぜ（公式の inference_realesrgan.py の dni と同じ。既定 0 = 残す版だけ）、spandrel 0.4.2 で読む（RealESRGAN Compact と認識）。256px の区画（すべて同じ大きさ。重なりは 12px を直線の重みでなじませる）で 4 倍にし、仕上がりの大きさへ面積平均（INTER_AREA）で縮める（4 倍を超える分は lanczos）。CPU が AMX / AVX-512 BF16 に対応していれば bf16 で計算する（fp32 との差 54 dB・最大 5 段）。--width・--height・--scale で大きさ。透過つき（WebM・PNG）は透過を lanczos で拡大して残す。動画は色の行列と範囲を元に合わせて正確に変換し（core の既定の変換は平均 0.5 段暗くなる）、音声と色の印を残す
- 実測: 正解つき（story540 の 5 コマ・building・fruits を INTER_AREA で縮めて戻す、元と比べる）: 4 倍・きれい: lanczos PSNR 35.14 dB・LPIPS 0.220（小さいほど見た目が近い）・勾配の比 0.73、AI 33.28 dB・LPIPS 0.181・0.90（AI はくっきりして見た目が近いが、画素は少しずれる）。4 倍・JPEG 品質 75: lanczos 0.375 → AI 0.249。H.264 crf 28 で圧縮した物: 2 倍 lanczos 0.266・AI 0.253、3 倍 0.377・0.302、4 倍 0.456・0.347。きれいな 2 倍は lanczos 42.86 dB・LPIPS 0.043、AI 37.66 dB・0.098（AI が肌のきめをならし、建物の線を濃くして元から離れる）、きれいな 3 倍は lanczos 0.126・AI 0.135 → auto の境目を 3 倍にした。--denoise は 0・0.5・1 のうち、どの倍率・劣化でも 0 が最も元に近かった（4 倍 JPEG だけ 0.5 と同等）。動画: 固定カメラの vtest を 1/2 に縮めて戻すと、動かない背景のコマごとのちらつきが元 0.233・lanczos 0.189・AI 0.338（AI は 1.45 倍）。透過つきの切り抜き（WebM）を 2 倍: 透明な画素 49.56% → 49.55%。速さ（AI の 4 倍の部分、bf16、区画 256、負荷 4〜5）: 入力 270×480 で 0.15 秒（分けない）・540×960 で 1.0 秒・720×1280 で 1.5 秒/コマ。fp32 は 3〜4 倍遅い。コマンド全体（270×480 → 1080×1920・24 コマ、別の重い試験と同時）で 2.3 秒/コマ
- 限界・注意: AI は細部を描き足すので、元に無い模様（髪の筋・肌のなめらかさ）になる。きれいな素材の 2〜3 倍では lanczos の方が元に近い（auto は lanczos を選ぶ。圧縮の傷が目立つ素材なら --method ai で 2 倍でも少し良くなった）。動画では、動かない背景が少しちらつく（上の 1.45 倍。気になる時は 31 時間方向のノイズ除去を後にかける）。顔は 34（顔の復元）ではないので、小さな顔の目鼻は作り直さない。4 倍を超える分は lanczos。CPU なので遅い（1080×1920 の入力は AI の部分だけで 3.7 秒/コマ。短く切って試す）。元に色の印が無い SD の映像を HD に拡大すると、再生側が色の行列を推測で変えることがある（ffmpeg で拡大した時と同じ）
- 確かめた素材と方法: test_upscale.py（images: 縮めて戻す正解つき 7 枚 × 2・4 倍 × きれい・JPEG、LPIPS は uv run --with lpips で一時的に足して測った。crossover: 2・3・4 倍 × きれい・H.264 crf 28。video: vtest のちらつき）、speed_upscale.py（区画と精度）、確認画像 26-upscale-truth.jpg（正解・lanczos・AI 3 種の拡大）・26-upscale-video-x4.jpg（270×480 の動画を 4 倍）。透過つきの cut-bath-540.webm を AI で 2 倍にして透過を確かめた

```bash
cd tools && uv run python -m vfx upscale [-h] [-o OUT] [--json JSON] [--start START]
                             [--duration DURATION] [--max-frames MAX_FRAMES]
                             [--scale SCALE] [--width WIDTH] [--height HEIGHT]
                             [--method {auto,ai,lanczos}] [--denoise DENOISE]
                             [--tile TILE] [--precision {auto,fp32,bf16}]
                             src
```

## 27. フレーム補間（`interpolate`） ○

- 何をする: コマとコマの間を作り、動きをなめらかにする
- 頼み方の例: 「カクカクした動きを、コマを増やしてなめらかにして」
- 中身: ffmpeg の minterpolate（mi_mode=mci・mc_mode=aobmc・me_mode=bidir・vsbmc=1）。最後のコマを tpad で 2 コマ分のばしてから補間し、コマ数で切る（docs/notes/production-log.md のスローモーションの作り方。末尾のコマ欠けを防ぐ）。--slow は setpts で長さをのばしてから補間する（音声は付けない）。つなぎ目の扱い: 前後のコマの差（幅 96px の灰色）が 10 より大きく、まわり ±12 コマの中央値の 5 倍より大きい所（カット・白いフラッシュ・急な変化）で区切り、区切りごとに補間して -c copy でつなぐ（区切りでは中間のコマを作らず、前のコマをのばす）。minterpolate 自身の場面転換の判定（scd）も既定の 10 から 5 に下げた。blend・dup も minterpolate の同名の方法（コマの時刻の扱いをそろえるため）
- 実測: 正解つき（24fps の映像の 1 コマおきを抜いて 12fps にし、24fps に戻して抜いたコマと比べる。vtest は 10→5→10fps）: 作ったコマの PSNR（mci / blend / dup）: まつげの施術 40.29 / 39.20 / 36.36、目が開く 41.59 / 36.72 / 34.67、眉の施術（速い手）34.14 / 33.15 / 30.93、カフェで笑う 34.78 / 29.41 / 26.36、人が歩く vtest 31.94 / 29.43 / 27.00 dB。元のコマはそのまま出る（46.6〜50.3 dB。H.264 の分だけ）。つなぎ目: 直す前（minterpolate だけ）はカットで 2 つの場面が混ざったコマができた（story の 3.04 秒）。区切った後は story540 全体の 2 倍でカット 4 か所の混ざり 0（361 → 722 コマ）、v4 の 2 倍で、別の規則で見つけたつなぎ目 23 か所（カット・白いフラッシュ）のうち混ざり 1（同じ場面で速く動くロゴの文字）（600 → 1200 コマ、区切り 22）。区切りの見つけ方: カットの無い 10 本（元の fps と半分の fps）で余分な区切り 1（眉の施術の速い手）。スローモーション 2.5 倍: 48 → 120 コマ・5.000 秒（ちょうど）、元のコマが 2.5 コマごとに 50.05 dB で出る。速さ: 540×960・24 コマを 2 倍で 8.4〜9.4 秒（作るコマ 1 枚 0.18 秒ほど）、story540 全体（361 コマ）の 2 倍で 92 秒
- 限界・注意: 簡易な方法（ブロック単位の動き補償）。動きの推定はブロック単位なので、速く動く物（手・指）や、同じ場面で速く動く文字・ロゴは形が崩れることがある（AI の補間はこの崩れが少ないとされるが、ここでは比べていない）。文字を入れた完成品ではなく、文字を入れる前の素材にかける。カットでは前のコマをのばすので、作ったコマ 1 枚分だけ切り替わりが遅れる。区切りの見つけ方は速い動きも区切ることがあり、そこは補間しない（少しカクつく）。--no-breaks で区切らない。AI の補間（RIFE など。Hugging Face に MIT の重みもある）は spandrel で読めず、モデルの構造を書き写す必要があるので入れていない。1080p は 540p の約 4 倍の時間がかかる
- 確かめた素材と方法: test_interpolate.py（drop: 6 本の正解つき、slow: 長さとコマの位置、cuts: story540 全体と v4 全体のつなぎ目）、test_interp_scd.py（scd のしきい値 10・7・5・3 の比較）、calib_breaks.py（区切りの見つけ方の較正）、確認画像 27-interpolate-truth.jpg（各映像の最も動くコマの拡大）・27-interpolate-cut.jpg（カットで混ざったコマと直した後）・27-interpolate-v4-cuts.jpg・27-interpolate-slow.jpg

```bash
cd tools && uv run python -m vfx interpolate [-h] [-o OUT] [--json JSON] [--start START]
                                 [--duration DURATION]
                                 [--max-frames MAX_FRAMES]
                                 [--max-side MAX_SIDE] [--fps FPS]
                                 [--slow SLOW] [--method {mci,blend,dup}]
                                 [--no-breaks]
                                 src
```

## 28. ノイズ除去（`denoise`） ◎

- 何をする: ザラザラした粒を減らし、細部は残す
- 頼み方の例: 「暗い所で撮ったザラザラを減らして」
- 中身: ffmpeg の dctdnoiz（既定。8×8、強いノイズでは 16×16 の DCT の係数をしきい値で切る）・nlmeans（非局所平均）・hqdn3d（空間だけ）。強さは自動: 明るさ Y の 2×2 Haar ウェーブレットの対角成分の |値| の中央値 ÷ 0.6745 を 32px の区画ごとに求め、白飛び・黒つぶれの区画を除いた下位 25% をノイズの強さ σ とする（動画は 5 コマの中央値）。dctdnoiz の sigma = 1.6σ、nlmeans の s = 0.75σ、hqdn3d の空間 = 2σ（既知のノイズで PSNR が最良の倍率を較正）。dctdnoiz は RGB でしか動かないので、動画は色を最近傍で広げて RGB にし、2×2 の平均で戻す（ffmpeg の自動の変換は何もしなくても 45.8 dB に劣化、この方法は 99 dB）。画像は OpenCV で読んだ画素を渡す。AI モデルは使わない
- 実測: ノイズの推定: RGB 各色に σ5/10/20 を加えた 8 枚で、明るさの真値 3.34/6.68/13.36 に対し 3.22〜3.83／6.37〜6.99／11.79〜13.12（油絵の starry_night だけは筆の模様をノイズと見て、ノイズ無しで 6.67）。画像（story540 の顔の寄り／building.jpg、自動の強さ）: σ5 34.1 → 43.95／41.62 dB、σ10 28.1 → 41.00／37.61 dB、σ20 22.2 → 38.26／33.42 dB（nlmeans は 42.34／38.63・39.87／34.62・36.99／30.85、hqdn3d は 1〜2 dB しか上がらない）。動画（story540 6〜8 秒・48 コマに σ10、yuv420p）: 29.97 → 37.00 dB（nlmeans 36.39、hqdn3d 32.54）。ノイズの無い story540 にかけると入力との差 44.37 dB（書き出し直しただけで 45.94 dB）。強いノイズで 16×16 にすると 8×8 より +1.3〜1.7 dB（σ20・30）。速さ: 540×960・48 コマで 7〜20 秒（dct）、3 秒（hqdn3d）、25 秒（nlmeans）。画像 1 枚 1〜2 秒
- 限界・注意: 画素ごとに独立のノイズで較正した。実際のカメラのノイズ（にじんだ色のむら・暗い所ほど強い）は弱めに推定されることがあるので、残る時は --strength 1.3〜1.5。細かい模様の多い絵（油絵など）は模様をノイズと見て強くかかる（--sigma で指定）。髪・ニットの細かい模様は σ が大きいほど柔らかくなる（--strength 0.6〜0.8 で残す）。1 コマずつの処理なので、動画では残ったノイズが毎コマ変わってちらつく（31 を使う）。学習モデルのノイズ除去（DRUNet・SCUNet など）は入れていない
- 確かめた素材と方法: test_denoise.py（既知のガウスノイズ: 画像 2 枚×3 段階・動画 48 コマ・ノイズ無しの対照）、test_noise_est.py（推定の精度、8 枚×5 段階）、calib_denoise.py・calib_denoise_luma.py（倍率の較正: 画像 3 枚×4 段階と動画 3 段階）、確認画像 28-denoise-images.jpg・28-denoise-video.jpg を目で確認（σ20 の 8×8 の四角いむらを見て 16×16 に変えた）

```bash
cd tools && uv run python -m vfx denoise [-h] [-o OUT] [--json JSON] [--start START]
                             [--duration DURATION] [--max-frames MAX_FRAMES]
                             [--max-side MAX_SIDE]
                             [--method {dct,nlmeans,hqdn3d}] [--sigma SIGMA]
                             [--strength STRENGTH]
                             src
```

## 29. ブレ除去（`deblur`） ○

- 何をする: ぶれてにじんだ輪郭を戻す
- 頼み方の例: 「手ぶれでにじんだ所を、輪郭が分かるくらいに戻して」
- 中身: auto（既定）: ぶれの形を推定し、ピンぼけと、動画で画面全体の一様な動きのぶれは rl、それ以外（画像の手ぶれ・見分けられない）は ai。ai: NAFNet（GoPro の動きのぶれで学習、width64）。megvii-research の公式の重み（MIT）を Hugging Face の tog/nafnet-models（license: mit）から版を固定して取り、sha256 で照合する。spandrel 0.4.2 で読み、学習と同じ 256px の区画（重なり 32px をなじませる）で fp32 で推論（bf16 は速くならず、出力が崩れた）。wiener: 定数 K の古典的なウィーナー、rl: リチャードソン・ルーシー（scikit-image 0.26）。どちらも明るさだけ（色はそのまま）、周りを折り返して広げ外側をなじませてから処理し、K = 0.01×σ^0.83・回数 = 45×σ^−0.75（σ は推定したノイズの強さ、最低 1。較正の最良値に合わせた式）。ぶれの形は --kernel と長さ・角度・半径・σ で指定するか、ケプストラム（256px の区画のハン窓の対数パワースペクトルの平均を逆変換）から推定する: 動きのぶれは負の山の位置（長さ・角度。1 画素より細かく）、ピンぼけは半径ごとの平均のくぼみ。種類は較正した規則で見分ける（くぼみ ≥ 12 → ピンぼけ、山 ≥ 5・向きの違う 2 番目の山との比 ≥ 1.4・長さ ≥ 6px → 動き、それ以外は「なし」）。動画は 5 コマで推定し、多数決と中央値
- 実測: 推定（8 枚に既知のぶれ、σ1 のノイズ、JPEG 品質 85 あり・なし）: ぶれ無し 16/16 を「なし」、動き（長さ 7〜31px・5 方向）79/80 を「動き」と判定し、長さの誤差の中央値 0.34px（90% 点 0.9px）・角度の誤差の中央値 0.3°（90% 点 2.1°）、ピンぼけ 半径 5・8・12 は 48/48（推定 4.68・7.75・11.46）、半径 3 は 5/16・2 は 0/16（「なし」）。OpenCV の実写の見本: licenseplate を動き 22.4px・134.9°（見本の値 22px・135°）、text_defocus をピンぼけ 半径 8.9px（見本の値 直径 19px）、text_motion は「なし」と判定（候補は 32.1px・86.8°。見本の値 31px・86°）。戻す（7 枚、σ1 のノイズ、推定した PSF、元との PSNR）: 直線の動き 15px で ぼけ 28.87 → wiener 33.33・rl 33.96・AI 32.20 dB、25px で 27.56 → 31.92・32.11・AI 33.28、ピンぼけ 半径 6 で 29.23 → 32.64・33.10（AI は 4 枚で 29.13 → 29.35）。推定した PSF は正しい PSF とほぼ同じ成績（15px: 33.33 対 33.32）。曲がった軌跡の合成の手ぶれ: 1 例は推定が「なし」で変えず（35.37）、もう 1 例は直線と推定した形でかえって悪化（30.15 → rl 29.00。正しい PSF なら 37.72）、AI も 4 枚で 34.94 → 30.35・30.01 → 27.41（位置を合わせても入力より悪い）。AI をぶれていない 4 枚にかけると元との差 34.45 dB（輪郭となめらかな所を作り変える）。H.264 の影響: 1 コマに 15px のぶれ（0・30・90°）を足し、圧縮なしなら AI 32.59 → 34.53・33.10 → 36.20・34.81 → 35.02、H.264 crf12 にすると 32.15 → 29.39・32.59 → 29.65・34.08 → 28.89（色の間引きだけなら 35.75 で、圧縮の傷が原因）。動画（story540 の 12 コマに横 15px のぶれを足して H.264 crf12）: 自動の推定 15.3px・180°、ぼけ 31.72 → wiener 33.78・rl 35.50、AI は 31.81 → 31.44（4 コマ）→ auto は動画の一様なぶれに rl を使う。実写の見本（目で確認）: 本物の手ぶれの text_motion・licenseplate は AI が最もきれいに戻し（数式・ナンバー 127-RFS が読める）、wiener・rl も読めるが縞が出た。ピンぼけの text_defocus は wiener・rl で読めるようになり、AI は戻せなかった。速さ: wiener 0.05〜0.09 秒/コマ・rl 1.0 秒/コマ（540×960）、AI 540×960 で 6.1 秒/コマ・600×482 の画像で 3.8 秒（負荷 5〜7）
- 限界・注意: 簡易な方法: wiener・rl は画面全体で同じぶれ（直線の手ぶれ・ピント外れ）を前提にしていて、被写体だけが動いたぶれ・場所で違うぶれ・曲がった軌跡の手ぶれには合わず、かえって悪くなることがある（上の合成の手ぶれ）。AI（NAFNet）は GoPro の動きのぶれで学習していて、ピンぼけは戻せず、ぶれていない・ぶれの弱い映像では輪郭やなめらかな所を作り変える（ぶれが見つからない時は注意を出す）。H.264 で圧縮した映像では、AI が圧縮の傷をぶれと取り違えて悪くなることがある（一様でないぶれは AI しか無いので、確認画像で見る）。AI の前に軽くぼかすと合成の H.264 では良くなったが、実写の見本では効かなくなったので入れていない。wiener は動きの向きに沿った縞（波紋）が出やすい（rl の方が少ないが約 10 倍遅い）。半径 3px 以下のピンぼけは見分けにくい。推定が「なし」の時は --kernel motion・defocus で候補の値を使える（text_motion はこれで戻った）。圧縮の強い素材はノイズの推定が 0 になるので、σ は最低 1 として扱う（結果がざらつく時は --strength を 0.5 などに下げる）。AI は CPU で遅い
- 確かめた素材と方法: test_deblur.py（estimate: 推定の正解つき 192 例と実写の見本 3 枚、calib: 正しい PSF での較正、compare: 7 枚 × 直線 2・手ぶれ 2・ピンぼけの推定した PSF の wiener・rl と AI（AI の手ぶれ・ピンぼけは 4 枚）、identity: ぶれていない 4 枚に AI、real: 実写の見本 3 枚をコマンドで）、calib_wiener.py（定数 K の較正）、proto_blur_features.py（見分け方の較正）、test_deblur_shift.py（AI の位置を合わせて測り直す）、test_deblur_preblur.py（AI の前処理）、story540 に横 15px のぶれを足した H.264 の動画（wiener・rl・ai をコマンドで）、確認画像 29-deblur-real.jpg（実写の見本 × 3 方法）・29-deblur-truth.jpg・29-deblur-video.jpg・29-deblur-preblur.jpg

```bash
cd tools && uv run python -m vfx deblur [-h] [-o OUT] [--json JSON] [--start START]
                            [--duration DURATION] [--max-frames MAX_FRAMES]
                            [--max-side MAX_SIDE]
                            [--method {auto,ai,wiener,rl}]
                            [--kernel {auto,motion,defocus,gauss}]
                            [--length LENGTH] [--angle ANGLE]
                            [--radius RADIUS] [--sigma SIGMA]
                            [--strength STRENGTH]
                            src
```

## 30. 圧縮ノイズ除去（`deblock`） ◎

- 何をする: 強い圧縮で出た四角いノイズを減らす
- 頼み方の例: 「圧縮で出た四角いカクカクを減らして」
- 中身: ffmpeg の spp（既定。8×8 の DCT を少しずつずらしてかけ、柔らかいしきい値で量子化の段差をならす。quality 3）・fspp・pp7。強さ qp は自動: 明るさの隣どうしの差を 8px 周期の位置ごとに平均し、最も大きい位置（ブロックの境目）の超過分 e とそれ以外の平均 m から目立ち方 x = e²/m、qp = round(1.5 + 0.35x)（1〜12。x < 0.1 は 1）。縮小の前にかける。色を半分の細かさで持つ JPEG（4:2:0）は yuv420p で処理（色のブロックも 8×8 になる）。画像は OpenCV で読んだ画素を渡す（ffmpeg の JPEG の読み込みは 0.1〜1 dB 悪かった）

- 限界・注意: 8×8 の四角の段差（JPEG・MPEG-1/2/4・H.263）向け。H.264/H.265 は保存の前に自分でブロックをならすので、絞った H.264 では +0.1 dB ほどしか変わらない（にじみ・消えた細部は戻らない）。縮小・拡大された映像は四角が 8px でなくなり目立ち方を測れない（--qp で指定）。強くかけると細かい模様もならされる。ffmpeg の pp（libpostproc）と deblock も比べたが、元の量子化の値が無いと +0.05〜0.7 dB で spp より弱かった。映像に記録された QP を spp に渡すと強すぎてかえって悪化し、H.264 では動かなかった

## 32. 逆トーンマッピング（`inverse-tonemap`） ○

## 33. トーンマッピング（`tonemap`） ◎

## 36. フリッカー除去（`deflicker`） ◎

- 何をする: コマごとの明るさのばらつきをそろえる
- 頼み方の例: 「照明のせいでチカチカする明るさをそろえて」
- 中身: gain（既定）: 幅 64px の灰色の小さなコマで、場面ごと（カット = 各コマを平均で割った差が、前後 5 コマの差の中央値の 4 倍かつ 8 以上）に、前後 11 コマ以上（既定 0.5 秒）の画素ごとの中央値（対数の明るさ）を基準とし、そのコマとの差の、画素についての中央値を揺れとする（白飛び・黒つぶれは除く。3 回繰り返す）。各コマに exp(−揺れ) を掛ける。直す量が ±30% を超えるコマを含むひと続きは演出（白いフラッシュ・フェード）とみなして直さない（--max-change）。ffmpeg の deflicker（前後のコマの平均の明るさに合わせる）も選べる。確認画像に明るさのグラフと時間の断面を付ける

## 47. 周辺減光の補正（`devignette`） △

- 何をする: 四隅が暗くなるのを、中央と同じ明るさに戻す
- 頼み方の例: 「画面の四隅が暗いのを直して」
- 中身: 信号の値（ガンマのかかった R・G・B）に、中心からの距離（四隅で 1。ffmpeg の vignette と同じ測り方）だけで決まる倍率 1/V を掛ける（上限 --max-gain）。V の求め方: --angle = ffmpeg の vignette と同じ cos⁴(角度 × 距離)。--reference = 無地の面を撮った画像・動画の明るさの対数に log V = a r² + b r⁴ + c r⁶ を当てはめる。自動（既定）= 明るさの対数の外向きの傾きを半径ごとに上下 20% を除いて平均し（自然な画像では 0 に近いという仮定）、log V = a r² + b r⁴ の傾きに当てはめる（動画は 32 コマを合わせて）。自動は、外に向かって単調に暗くならない推定や四隅の倍率 1.02 未満では補正しない。上限は自動 2 倍・ほか 4 倍
- 実測: --angle: ffmpeg の vignette（RGB、ディザなし）で 30・45 度の減光を加えた 4 枚を同じ角度で戻すと 47.78〜50.38 dB（ffmpeg 自身の mode=backward は 44.70〜46.45 dB）。動画（story540 6〜8 秒・36 度）17.68 → 39.89 dB。--reference: 照明のむら ±8%・ノイズ σ2.5・JPEG 品質 90 の無地の面（画像と 24 コマの動画、540×960 と 1280×720）から測った四隅の明るさの誤差 0.66〜2.31%（cos⁴40° の 0.3444 を 0.3365〜0.3392、別の型の 0.4066 を 0.3977〜0.4039）、同じ減光を加えた画像を戻すと 48.94〜53.99 dB（最初は 3% のぼかしで四隅が +9% 明るく出たので、ぼかしを 1px にした）。自動: 減光の無い画像 11 枚の推定は四隅 0.313〜1.000（0.9〜1.1 に入ったのは 4/11。building 0.313・fruits 0.444・vtest 0.470 は写っている物の暗さを減光と見なし、上限の 2 倍で明るくした）。cos⁴30°（0.563）を加えた時の元の推定との比の誤差は log で中央値 0.0010（加えた分は正確に測れる）が、正解との差は中央値 0.334・最大 1.075。動画の自動（story540・32 コマ）: 元は補正なし、cos⁴30° を加えると 0.508（正解 0.563）。速さ: 540×960・48 コマで 2.1 秒、story540 全体の自動 4.4〜8.2 秒
- 限界・注意: 条件: 自動の推定は、四隅に暗い物（芝生・木・暗い背景）や明るい物がある構図で大きく外れる（減光の無い画像で四隅 0.31〜1.0 と推定）。確実なのは --reference（同じカメラ・レンズ・ズームで無地の壁や白い紙を撮る）か --angle（ffmpeg の vignette で付けた減光を外す時）。自動が正確なのは四隅まで空や壁が続く画像（home・aero1 で 1.000）。作品の演出として付けた周辺減光も消す。中心のずれた減光・左右非対称な減光・色ごとに違う減光は扱わない。四隅の明るい所は白飛びすることがある。試して採らなかった方法: カメラの動きで同じ物が別の距離に写ることを使う推定（DIS のオプティカルフロー）は、減光の無い短い場面で 0.77〜1.18、加えた減光の比で ±20% ぶれた。方向（扇形 8 つ）ごとの推定の多数決は扇形ごとの推定が不安定

## 48. ガンマ補正（`gamma`） ◎

- 何をする: 白と黒は保ったまま、中間の明るさを変える
- 頼み方の例: 「全体を少し明るく、でも白は飛ばさずに」
- 中身: 出力 = 入力^(1/ガンマ) の 256 段の表（cv2.LUT）を R・G・B にかける（--channel rgb、既定）か、YCbCr（BT.601・全範囲、float で計算）の Y' だけにかける（luma）。黒（0）と白（255）は動かない。--gamma を省くと、範囲の小さなコマ（最大 64 枚）の明るさ Y' の中央値を --target（0.45）にするガンマ = log(中央値) / log(目標) を 1 つ選ぶ（1/3〜3）。動画は全コマ同じ表なのでちらつかない
- 実測: 既知のガンマ γ0（0.5・0.7・1.5・2.2）を独立な実装（float で計算して 8 bit に丸める）でかけた 4 枚を --gamma 1/γ0 で戻すと 40.60〜59.43 dB、独立な実装で戻した物との差は全画素で 0（誤差は暗くした時の 8 bit の丸めだけ。γ0 0.5 で最大 11 段・平均 0.29〜1.05）。luma: 28.51〜57.04 dB（fruits の γ0 0.6 は、彩度の高い色が明るくした時に色域の外に出た分が戻らない）。自動の推定: 元の中央値を目標にすると、かけたガンマを相対誤差 平均 1.79%・最大 4.46% で当てた（10 例）。動画（story540 6〜8 秒、ffmpeg の lutrgb で γ0 0.6 → 戻す）: 16.73 → 42.21 dB（ガンマ 1.0 で書き直しただけで 46.02 dB）。ffmpeg の eq=gamma=2 は TV の範囲の Y を 0〜255 のまま計算するため、黒 0 → 55・16 → 82 に持ち上がる（この道具は 0 → 0・16 → 64、式 63.9）。速さ: 540×960・48 コマで 1.3 秒（luma 1.5 秒）
- 限界・注意: 中間だけを動かすので、白飛び・黒つぶれは直らない（33・40 を使う）。rgb で大きく明るくすると色が少し薄く、luma では彩度の高い色が色域の外に出て切れる。自動は中央値だけを見るので、夜の雰囲気なども明るくする（--target を下げる）。8 bit で暗くした映像を戻しても、消えた暗部の段差は戻らない
- 確かめた素材と方法: test_gamma.py（画像 4 枚 × 4 段、luma、自動の推定 10 例、動画、ffmpeg eq との比較）、確認画像 48-gamma.jpg を目で確認

```bash
                           [--duration DURATION] [--max-frames MAX_FRAMES]
                           [--max-side MAX_SIDE] [--gamma GAMMA]
                           [--target TARGET] [--channel {rgb,luma}]
                           src
```

## 49. ヒストグラム平坦化（`equalize`） ◎

- 何をする: 明るさの分布を広げて、明暗の差をはっきりさせる
- 頼み方の例: 「眠い感じの映像の明暗をはっきりさせて」
- 中身: Lab の L（明るさ）だけを平坦化し、a・b（色）は保つ（変えた量を元の L に足すので端数の精度が残る）。clahe（既定）: OpenCV の CLAHE（--clip 2.0・--tiles 8×8）。global: OpenCV の equalizeHist と同じ式（累積分布）を、端数の L で補間して当てる。動画の global は分布を時間でならし（--smooth 0.5 秒の指数移動平均）、場面の切れ目（Lab の差）でやり直す。--strength で元と混ぜる
- 実測: 平坦化は明るさの順位だけで決まるので、コントラストを下げた画像 C（76〜178 に縮めた物と、ガンマ + 縮小）を平坦化すると、元 I を平坦化した物と同じになるはず: L の PSNR(eq(C), eq(I)) は global 27.87〜42.69 dB（平均 38.43、7 枚 × 2 種類）、比べた ffmpeg の histeq 24.81〜32.99（平均 28.56）。CLAHE は伸ばす量に上限があるので一致しない（14.38〜21.83）が、明るさの標準偏差は C の 13〜33 → 27〜52（元 41〜82）に戻る（global は 72〜75 まで伸ばす）。OpenCV の関数を L に直接かけた物との差: L の平均 0.56〜1.38 段・最大 12 段（色域の外に出た色を戻す時の切り捨て）。平らな所の細かい揺れ（高周波の標準偏差）: story-face 0.55 → global 1.68・clahe 1.42、aero1 3.59 → 5.60・8.10。動画のちらつき（固定カメラの vtest を低コントラストにした 200 コマ、背景の明るさのコマ間の変化）: global のならしなし 0.061 → 既定 0.5 秒 0.046 → 2 秒 0.039、clahe 0.044（元 0.020）。story540 の場面の切れ目 4/4 をコマ単位で検出。速さ: 540×960・48 コマで 1.7〜2.1 秒、768×576・200 コマで 4.8〜6.2 秒
- 限界・注意: 明るさだけを変えるので、薄くなった色（彩度）は戻らない（色を含めた PSNR は global で 19.55〜34.51 dB）。global は全体を強く伸ばし、空や肌のなめらかな所のノイズ・圧縮の段差が目立つ（--strength 0.5〜0.7）。CLAHE は区画ごとなので、大きな明暗の差がある所の境に軽いむらが出ることがある。動画の global はならしてもわずかにちらつく
- 確かめた素材と方法: test_equalize.py（7 枚 × 2 種類の低コントラスト、OpenCV との照合、平らな所の揺れ、vtest のちらつき、story540 の切れ目、ffmpeg の histeq との比較）、確認画像 49-equalize.jpg を目で確認

## 50. フィルムグレイン（`grain`） ◎

- 何をする: フィルムのような細かい粒を加える
- 頼み方の例: 「フィルムっぽい粒子感を少し足して」
- 中身: 明るさ（動画は Y の面、画像は YCrCb の Y）に、平均 0 のガウスの白色ノイズをガウスでぼかした粒を足す。粒の大きさは自己相関の半値全幅（px）で指定し、離散の自己相関で合うようにぼかしの σ を求める（--size 1 以下は 1 画素ごと）。強さ（--strength。標準偏差、0〜255 の段）は中間の明るさで指定の値、黒・白に向かって 0.35 倍まで弱める（0.35 + 0.65×4y(1−y)。--flat で一定）。乱数の種と、コマの番号から粒を作るので、コマごとに変わり（--static で同じ）、同じ種なら同じ結果。色の粒は --chroma（既定 0）。動画は H.264 に -tune grain を付けて書く（色の面は変えない）。HyperFrames の作品の中で粒子を足す時は、決まりどおり npx hyperframes media-treatment の details.grain（/media-use スキル）を使う。この道具は、素材のファイルそのものに前もって粒子を焼き込む用
- 実測: 平らな灰色の動画（540×960・24 コマ、可逆）に強さ 4: 足した粒の標準偏差 3.94・3.94・3.92（大きさ 1・1.5・3。H.264 crf16 の後）、画像（PNG）4.01〜4.02、平均のずれ 0.02 以下、自己相関の半値全幅 1.00・1.51・3.04px（画像 1.00・1.50・2.98）、前後のコマの粒の相関 0.000（--static は 0.993）、色の面の変化 0。明るさごとの強さは式どおり（Y 118: 3.90、式 3.99）、真っ黒・真っ白に近い所は、はみ出す分を切るのでさらに弱い（Y 16: 0.49）。H.264 での残り方（実写に足した粒と理想の粒の相関）: crf16 0.828、-tune grain つき 0.883（ファイルは 1.27 倍）。縞: 暗いなめらかなグラデーションを 8bit に丸めた物（1 段の縞が約 53px ごと）で、縞が見える原因の平らな台地（5×5 が同じ値）が 92.5% → 強さ 1: 71.9%・2: 4.6%・4: 0.1% に減った。目のぼかし（σ4px）を通した階段のずれは 0.216 → 0.218〜0.225 で変わらない（粒は段を消すのではなく隠す）。速さ: 540×960 で 0.04〜0.05 秒/コマ
- 限界・注意: 縞（バンディング）を目立たなくするだけで、段そのものは消さない（消すのは 45。両方なら 45 の後にかける）。1 段の縞を隠すには強さ 2 以上が要った。粒は H.264 で少し形が変わる（上の相関）。強くすると圧縮後のファイルが大きくなる。本物のフィルムの粒の形（銀塩の粒子の集まり）や色ごとの粒の違いまでは真似ていない。透過は残さない（動画は MP4）
- 確かめた素材と方法: test_grain.py（stats: 平らな灰色と階段の合成動画・PNG で標準偏差・平均・半値全幅・コマ間の相関・色の面・明るさごと、H.264 の設定ごとの残り方、band: 8bit の縞の台地の割合と目のぼかし後の誤差、video: story540 2 秒）、test_grain_encode.py（実写で -tune grain の有無）、確認画像 50-grain-banding.jpg（明暗 8 倍）・50-grain-frames.jpg（3 コマの粒）・50-grain-video.jpg

```bash
cd tools && uv run python -m vfx grain [-h] [-o OUT] [--json JSON] [--start START]
                           [--duration DURATION] [--max-frames MAX_FRAMES]
                           [--max-side MAX_SIDE] [--strength STRENGTH]
                           [--size SIZE] [--chroma CHROMA] [--flat] [--static]
                           [--seed SEED]
                           src
```
