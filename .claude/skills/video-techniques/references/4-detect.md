`uv run python -m vfx <コマンド> --help` で引数の詳細が出る（tools/ で実行）。

## 76. シーン検出（`scenes`） ◎

- 何をする: カットが切り替わる時刻を見つける
- 頼み方の例: 「この動画のカットの切り替わりの時刻を一覧にして」
- 中身: PySceneDetect 0.7.3（BSD-3-Clause）の AdaptiveDetector（既定。--method で content・histogram・hash も選べる）に、幅 256px に縮めたコマを渡す。後処理を 3 つ足した: (1) adaptive の比を、差がほぼ 0 の前後のコマ（重複したコマ）を除いて求め直す（低いコマ数の映像で小さな動きがカットに見えるのを防ぐ）、(2) 0.25 秒以内に直前の画へ戻る変化はフラッシュとしてカットにしない。カットの直後 0.25 秒の変化（白を通したカットの戻り）はまとめる、(3) 0.3 秒より短い場面はまとめる。変化の大きさの下限（min_content）は PySceneDetect の既定 15 から 10 に下げた（同じ画角のジャンプカットを拾うため）。出力: 時刻の JSON・印を付けた確認用 MP4（カットから約 0.12 秒、赤い枠と「カット n（秒）」の帯。全コマに場面の番号。音声は残す）・各場面の先頭コマの一覧 JPG
- 実測: story540: カット 4/4 をコマ単位で一致（73・139・213・297 コマ = 3.042・5.792・8.875・12.375 秒。「3.0 秒」の境目は 72 と 73 コマの間）。v4: 11/11 をコマ単位で一致（白いフラッシュで始まる 2.5・6.0・16.0 秒を含む）。難しい合成映像（カット 6・同じ画角のジャンプカット 1・1 コマ 40px の速いパン・同じ場面の白 2 コマ・白 2 コマを通るカット・0.5 秒のディゾルブ）: カット 7/7 一致、パンと同じ場面の白は数えず、白を通るカットは 1 回だけ。カットの無い映像（vtest 79 秒・a-eye・b-lashlift・c-brow・手を振る tree.avi）: 誤検出 0。後処理 (1) の前は tree.avi（449 コマ中 381 コマが重複）で 4 件（min_content 10 なら 9 件）の誤検出だった。min_content 15 ではジャンプカット（変化 10.3）を見逃した。content・histogram も 21/21・誤検出 0 だがジャンプカットを見逃し、hash は tree.avi で 2 件誤検出。速さ: v4（540×960・600 コマ）で JSON と一覧だけなら 4.2 秒、確認用 MP4 も作ると 15.5 秒（他の作業と CPU を分け合った状態の壁時計）
- 限界・注意: 溶けるつなぎ目（フェード・ディゾルブ）はカットとして数えない（92 を使う）。0.25 秒以内に元の画へ戻る差し込みはフラッシュ扱い（--flash 0 で無効）。0.3 秒より短い場面はまとめる（--min-scene）。変化が 10 未満のジャンプカットは見逃す（--min-content を下げると拾えるが誤検出が増え得る）。白いフラッシュで始まる場面は一覧の先頭コマが白くなる（代表コマは 83 を使う）。TransNetV2（MIT、ONNX）も比べたが v4 の白いフラッシュのカット 2 つを見逃したので使っていない
- 確かめた素材と方法: story540・v4（作品の場面の始まりを正解に）、正解つきの合成映像 scenes-hard（make_scenes_hard.py）、カットの無い vtest・a-eye・b-lashlift・c-brow・tree.avi。test_scenes_sweep.py で方法と設定を比べ、review_scenes.py で確認用 MP4 のカット前後のコマを目で確認

```bash
cd tools && uv run python -m vfx scenes [-h] [-o OUT] [--json JSON] [--start START]
                            [--duration DURATION] [--max-frames MAX_FRAMES]
                            [--max-side MAX_SIDE]
                            [--method {adaptive,content,histogram,hash}]
                            [--threshold THRESHOLD]
                            [--min-content MIN_CONTENT]
                            [--min-scene MIN_SCENE] [--flash FLASH]
                            [--no-video]
                            src
```

## 78. 物体検出（`objects`） ◎

- 何をする: 写っている物の種類と位置を見つける
- 頼み方の例: 「画面に何が写っているか、名前と枠で示して」
- 中身: COCO の 80 種類: detectors.ObjectDetector（accurate = torchvision の Faster R-CNN v2、fast = MediaPipe の EfficientDet-Lite2）。種類ごとの重なり除去に加え、ほぼ同じ枠（IoU 0.7 以上）に別の名前が付いた物は確からしさの高い方だけ残す。名前は日本語。--classes で種類を絞る（日本語・英語）。--query で 80 種類にない物を英語の言葉で探す（Grounding DINO tiny。IDEA-Research/grounding-dino-tiny、Apache-2.0。transformers 5.2 で動作。入力の短い辺は 800px まで、下限 0.45）。動画は --every 秒ごと（既定 accurate 0.2・fast 0.1・--query 0.5）に調べ、間のコマは同じ名前で重なりの大きい枠どうしを直線で補って MP4 に描く（音声は残す）。出力: 枠と名前を描いた画像・MP4・一覧 JPG、JSON（コマごとの名前・確からしさ・枠〔元の画素〕と、名前ごとの映ったコマの数・同時に映った最大の数・最初と最後の時刻）
- 実測: 貼り付け試験（mp-cat_and_dog.jpg の猫と犬〔枠は目で確認〕を、story540 などのコマ 7 枚に高さ 48〜320px・左右反転ありで貼った 40 枚。名前が合い IoU 0.5 以上を当たり）: accurate 38/40（高さ 48px の 2 枚を見逃し）・当たりの IoU 平均 0.959・違う名前 0・離れた所の余計 0・1 枚 2.4〜2.6 秒、fast 19/40（高さ 128px 以上でないと見つからない。48・80px は 0/16）・0.08 秒、--query "cat, dog" 28/40（下限 0.45。0.35 なら 30/40）・猫と犬の取り違え 5〜6 件・2.2〜3.8 秒。mp-cats_and_dogs.jpg: 猫 2・犬 2（重なり除去の前は、コーギーに「犬 0.99」と「猫 0.54」が重なって出た）、mp-cat_and_dog.jpg: 猫 1・犬 1（＋ 画面全体を「ベンチ 0.50」と誤検出）。fruits.jpg: 80 種類ではかんきつ類もキウイもみな「オレンジ」、--query "orange, lemon, lime, kiwi" でキウイ・レモン・オレンジ 2・ライムを正しく分けた。vtest（目で数えて 6 人の 3 コマ）: accurate 6・6・6 人、fast 5・6・5 人（ほかに白いバンを「トラック」、余計な「フリスビー」「ベンチ」各 1）。story540 で --query "eyelash curler, table"（0.5 秒ごと 31 コマ。正解はビューラーの場面 0〜3.04 秒・カフェ 12.38〜15.04 秒）: ビューラー 7/7・テーブル 6/6、余計 0（下限 0.35 では別の場面の目元を eyelash curler とした余計が 11 件〔確からしさ 0.35〜0.41。正しい物は 0.53 以上〕あったので、既定を 0.45 にした）。story540 の 3〜9 秒（0.2 秒ごと 30 コマ、accurate）: 手に持ったスマートフォン（0.98〜0.99）・浴室の流し台を見つけ、余計な「はさみ」1 回。日差しの場面では同じ人に全身と上半身の 2 つの枠が出るコマがあった（重なり 0.7 未満なので残る）。枠と名前を描いた MP4（間のコマは直線で補う）まで 70.6 秒
- 限界・注意: 80 種類は COCO の物だけ（化粧品・ビューラーなどは --query）。--query は英語だけ（Claude が訳して渡す。日本語は 80 種類の名前だけ自動で直す）で、似た言葉（eyelash と目元など）に引っぱられることがある。高さ 50px 未満の小さな物は見逃しやすい（fast は 130px 未満）。accurate は CPU で 1 コマ 2〜4 秒・--query は 2〜5 秒なので、長い動画は --every を大きく、--max-side を小さく。枠は箱（形の切り抜きは 51〜75 を使う）。同じ人に全身と上半身の 2 つの枠が出ることがある（人数は 95 で数える）。動画の間のコマの枠は直線で補った位置なので、速い動きではずれる
- 確かめた素材と方法: test_objects.py（猫・犬の貼り付け 40 枚 × accurate・fast・--query、story540 の --query を時間の正解と照合）、story540 の 3〜9 秒の MP4、mp-cat_and_dog・mp-cats_and_dogs・fruits（目で確認）、vtest の 3 コマ（人を目で数えて照合）。確認画像 78-objects-*.jpg

```bash
cd tools && uv run python -m vfx objects [-h] [-o OUT] [--json JSON] [--start START]
                             [--duration DURATION] [--max-frames MAX_FRAMES]
                             [--max-side MAX_SIDE] [--model {accurate,fast}]
                             [--score SCORE] [--classes CLASSES] [-q QUERY]
                             [--every EVERY] [--no-video]
                             src
```

## 79. 文字認識（`ocr`） ○

- 何をする: 画面に写った文字を読み取り、文字のデータにする
- 頼み方の例: 「画面に出てくる文字を読み取って書き出して」
- 中身: EasyOCR 1.7.2（Apache-2.0）の日本語＋英語（CRAFT で文字の場所〔MIT〕、japanese_g2 で認識〔Apache-2.0〕）。重みは GitHub のリリースから取ってキャッシュに置く（EasyOCR 自身には取得させず、読み込む時に md5 を照合させる）。EasyOCR に numpy を渡すと CRAFT には BGR のまま渡り灰色も BGR として作られるので、CRAFT には RGB、認識には正しい灰色を自分で渡す。CRAFT の拡大率は長辺がおよそ 1440px になる倍率（1〜2）。認識は灰色と白黒反転の両方で行い、枠ごとに確からしさの高い方（白字に黒い縁のテロップ向け）。確からしさ 0.1 未満は捨てる。動画は --every 秒ごと（既定 0.5）に読み、同じ場所（IoU 0.3 以上）の同じ文字（NFKC・空白なしで、編集距離が長さの 1/4 以内）をまとめて映っている区間を出す（文字は確からしさの合計がいちばん多い読み）。出力: JSON（まとめた文字・区間・四隅・読みの候補と、コマごとの読み）、文字と枠を描いた画像（動画は文字のあるコマの一覧）、--srt で時刻つきの SRT
- 実測: 採点: NFKC・空白なしで、正解の行ごとに最も近い読みの行を当てた文字の正解率（1 − 編集距離 ÷ 文字数）。v4 の 2 コマ（14.7 秒「初回限定 まつげパーマ＋眉WAX / モチ約2倍 ／ 黄金比の似合わせ眉 / 7,980円（税込）」、17.6 秒「KATE stage LASH / 蒲田西口店 / 蒲田駅西口 徒歩2分 …」の 10 行・118 文字。明朝体の飾り文字）: 0.958（誤り 5: 「＋」を形の同じ漢字「十」と 2 回、大きな桃色の「円」を落とす・「p」と読む、「／」を落とす）。1 コマ 3.1 秒。設定の比べ合い（反転なし）: 拡大率 1.0 では 0.847、1.5 で 0.958、先に 2 倍に拡大しても 0.958 のまま（2〜7 倍遅い）、beam search も変わらない。合成（story540 の 3 コマに 5 行・78 文字を書く。画面に収まらない行は折り返す）: 淡い帯に黒字 14〜60px で 0.933〜0.969、白字に黒い縁 14・18・24・32・44・60px で 0.641・0.728・0.826・0.815・0.815・0.754（反転して読む工夫の前は 0.426・0.703・0.687・0.662・0.795・0.677）。遠近をつけた札「OPEN / 営業中」（幅 240px）: 奥行き方向 0・25・45 度（上下 0・20 度）で 6/6 とも 1.000、60 度で 0.29〜0.43。文字の無い story540: 読んだ物 0 件（10 コマ・16 コマの 2 回）。動画: v4 の 13〜20 秒を 0.5 秒ごと（14 コマ）で、まとめた文字 24 件。区間は作品の場面の始まり（data-start 13.5・16.0 秒）に合う（13.0〜13.5 秒は前の場面の札、14.0〜16.0 秒は値段の場面、16.5〜20.0 秒は店の案内。文字が出てくる動きの分だけ遅れる）。同じ値段でも「7,980」（1.00）と「7,980p」（0.30）のように読みが分かれると別の件になる。44.5 秒（モデルの読み込みを含む）
- 限界・注意: EasyOCR の精度の限界: 白字に黒い縁のテロップは 6〜8 割の正解率（黒字・淡い帯の上の字は 9 割 3 分以上）。「＋」と「十」、「ー」と「一」、「:」と「;」など形の同じ字を取り違える。強い遠近（奥行き 60 度）・飾りの強い大きな字（光る桃色の「円」）は落とすことがある。縦書きは試していない。より強い OCR（PaddleOCR の PP-OCRv5 など）は入れていない（新しい依存関係が要る）。CPU で 540×960 の 1 コマ約 3 秒（他の作業と CPU を分け合うと 10〜25 秒）なので、長い動画は --every を大きく
- 確かめた素材と方法: test_ocr.py（v4 の正解つき 2 コマ、合成 36 枚〔2 つの書き方 × 6 つの大きさ × 3 コマ〕、遠近の札 8 枚、文字の無い story540）、採点は ocr_eval.py。設定の比べ合いは ocr_eval.py の実行・work/ocr_polarity.py・ocr_mag_big.py・ocr_outline_nopolarity.py。確認画像 79-ocr.jpg

```bash
cd tools && uv run python -m vfx ocr [-h] [-o OUT] [--json JSON] [--start START]
                         [--duration DURATION] [--max-frames MAX_FRAMES]
                         [--max-side MAX_SIDE] [--every EVERY]
                         [--min-conf MIN_CONF] [--mag MAG] [--srt]
                         src
```

## 80. ハイライト検出（`highlights`） ○

- 何をする: 見どころになりそうな区間を選ぶ
- 頼み方の例: 「長い映像から、見どころの区間を 3 つ選んで」
- 中身: 盛り上がりの点数を --bin（0.25 秒）ごとに出す。材料: 音の大きさ（ffmpeg の ebur128 の瞬時ラウドネス M）、動きの量（長辺 160px の明るさの前のコマとの差。区間ごとの中央値でカットの跳ねを抑える）、カットの密度（76 の方法で見つけたカットの、区間の長さの窓の中の数）、任意で言葉との近さ（--query。SigLIP 2）。各材料を動画の中の順位（0〜1）にして重みつき平均（--weights）。変化が小さい材料（音 3dB 未満など）と音声の無い動画の音は使わない。区間の長さ（--length 3 秒）の平均が高い所から重ならないように --top 個選び、端から 0.5 秒以内のカットに端を合わせる。--reel で区間をつないだ MP4（音は 0.03 秒で溶かす）。出力: JSON・グラフと区間のコマの確認画像
- 実測: 正解つきの合成映像（24 秒・音つき。静かな所に、速いカット 6 つ＋大きな音の 6〜9 秒と、笑う人＋大きな音の 15〜17 秒）: 上位 2 区間が 6.0〜9.0 秒（IoU 1.00）と 15.0〜17.875 秒（IoU 0.70。正解は 2 秒・区間は約 3 秒なので、正解を全部含めば 0.67〜0.7）。画だけ（audio=0）でも 6.0〜9.0・15.0〜18.125（IoU 1.00・0.64）、音だけ（motion=0,cuts=0）でも 6.0〜9.0・15.0〜17.875。v4（完成した広告 20 秒）: 上位 3 区間 1.0〜4.1（冒頭の「卒業」）・6.0〜9.1（曲の山＝「上がる。」）・10.0〜12.6（「好き」）。価格の強調 13.5〜16.6 は 4 位（0.52。3 位は 0.53）。--query 'a big price tag text|大きな価格の文字' では 13.5〜16.0 が選ばれ（言葉の順位 0.91）、代わりに 6〜9 が外れた。story540（音なし）: 音を使わずに 4.4〜7.4（髪を結ぶ〜日差しの場面へのカット）・7.4〜10.4・12.4〜14.9（笑う）。--reel: 8.900 秒（区間の合計 8.875 秒）・映像と音声あり。速さ: 合成 24 秒で 4.3〜4.7 秒、v4 で 7.0 秒（--reel を含む）、story540 で 3.2 秒
- 限界・注意: 音・動き・カットの量で見る簡易な方法で、意味（笑い・決めぜりふ・価格の強調など）は見ない（--query で言葉を足すと拾えるが、他の区間が押し出されることがある）。編集済みの広告のように最初から最後までカットが多く音量が一定の作品では、点数の差が小さい（v4 の 3 秒平均は 1〜15 秒の間 0.50〜0.66）。音の大きさは BGM と声を区別しない。区間の長さは固定（端だけカットに合わせる）
- 確かめた素材と方法: make_highlights.py（正解つきの合成映像）と test_highlights.py（既定・画だけ・音だけ、v4・story540、--reel の長さと音声を ffprobe で確認）、v4 の --top 5 と --query、--max-frames。確認画像 80-highlights-synth.jpg・80-highlights-v4.jpg・80-highlights-v4-query.jpg・80-highlights-story.jpg

```bash
cd tools && uv run python -m vfx highlights [-h] [-o OUT] [--json JSON] [--start START]
                                [--duration DURATION]
                                [--max-frames MAX_FRAMES]
                                [--max-side MAX_SIDE] [--top TOP]
                                [--length LENGTH] [--bin BIN]
                                [--weights WEIGHTS] [-q QUERY] [--snap SNAP]
                                [--reel]
                                src
```

## 83. キーフレーム抽出（`keyframes`） ◎

- 何をする: 場面ごとに、その場面を代表するコマを選ぶ
- 頼み方の例: 「場面ごとに 1 枚ずつ、代表の画を選んで」
- 中身: 76 と同じ方法で場面に分け、各場面の両端（場面の 1 割・最大 0.1 秒）を除いたコマから選ぶ。鮮明さ（ラプラシアンの分散を約 6×10 の区画ごとに求め、上位 10% の区画の値の平方根。長辺 960px で測る）が上位 4 割のコマのうち、場面の平均（幅 48px の Lab の小さな画）にいちばん近いコマ。--per-scene で場面を等分して複数選ぶ。出力: 元の大きさの PNG（フォルダ）・一覧 JPG・JSON
- 実測: story540 の各場面で 4 割のコマ（計 131 コマ）をぼかし（σ=2.5）、2 コマずつ（計 10 コマ）を別の場面のコマに差し替えた試験: 5 場面すべてで、正しい場面の、ぼかしていない・差し替えていないコマを選んだ（5/5）。選んだコマの鮮明さは、その場面のコマの上位 18〜32%。v4: 12 場面から 12 枚。どれも文字の動きが落ち着いた後の画で、白いフラッシュのコマは選ばなかった（目で確認）。速さ: v4 で 7.7 秒、story540 で 4.6 秒
- 限界・注意: 「平均に近い」なので、場面の途中で大きく変わる（後から文字が出る等）と中間の状態を選ぶことがある（--per-scene 2〜3 で前後を拾う）。動きのぶれもぼけとして避ける。とても短い場面（5 コマ未満）は端のコマも候補に入る。小さなコマをすべて覚えるので、縦長 30fps で 1 分あたり約 110MB（横長は約 35MB）のメモリを使う
- 確かめた素材と方法: make_keyframes_test.py の合成映像（ぼかし・差し替えの正解つき。test_keyframes.py）、v4、story540（--start・--duration・--per-scene 2）

```bash
cd tools && uv run python -m vfx keyframes [-h] [-o OUT] [--json JSON] [--start START]
                               [--duration DURATION] [--max-frames MAX_FRAMES]
                               [--max-side MAX_SIDE]
                               [--method {adaptive,content,histogram,hash}]
                               [--threshold THRESHOLD]
                               [--min-content MIN_CONTENT]
```

## 85. 人物の再識別（`reid`） ○

- 何をする: 別のカットや映像に出てくる同じ人を結び付ける
- 頼み方の例: 「別々のカットに出てくる同じ人を見つけて、同じ番号にして」
- 中身: カットの変わり目（15 と同じ判定）ごとに、人を検出して（共有 detectors。既定 accurate）15 と同じ追跡で「区間」（同じカットで続けて追えた 1 人分）にまとめ、区間ごとに顔の特徴量（YuNet〔MIT〕で顔を見つけ、SFace〔Apache-2.0〕で 128 次元）と体の特徴量（OpenCV Zoo の YouTu ReID〔Apache-2.0〕で 768 次元。服装・体つき）を平均する。体は他の人と重ならないコマを優先する。区間どうしの似ている度合い（コサイン）を、顔は 0.363（OpenCV の推奨値）、体は 0.60 を基準に点にし（両方ある時は顔 0.75・体 0.25 の重み）、同じコマの別の場所に映った区間は同じ人にしない条件つきの平均連結クラスタリングで「人物 1, 2, …」にまとめる。人として見つからない顔の寄りは、顔の周りを人の枠にする。複数の動画・画像をまたいでもつなぐ。出力: 人物ごとに場面の切り抜きを並べた一覧 JPG、人物ごとの出てくる時刻と枠の JSON（区間どうしの顔・体の類似度も）、--video で通しの番号を書いた MP4。DINOv2 small（Apache-2.0）の特徴量も比べたが、見分けが悪かったので使わない
- 実測: 体の特徴量（vtest を 10fps で追った 13 人を前半・後半に分けた組）: YouTu ReID は後半から同じ人を 1 番に選べた割合 0.923・AUC 0.985、DINOv2 small は 0.769・0.941。切り抜きを目で見て、同じ黒いコートの人と分かった番号（2・8・19）をまとめ、途中で別の人に入れ替わっていた番号（1・6）を除いて数え直すと、同じ人 23 組は 0.655〜（中央値 0.817）、別の人 208 組は中央値 0.278・最大 0.676（AUC 1.000）。しきい値 0.60 で同じ人 23/23・別の人を同じと誤る 5/208、0.65 で 23/23・1/208。story540（AI 生成の広告、カット 5 つ、4 コマ/秒で調べて 228〜262 秒）: カットの変わり目 4 か所はすべて 1 コマ以内。主人公が映るカットのうち、洗面所・日差し・カフェの 3 つを 1 人にまとめた（顔の類似度 0.69〜0.76）。顔の極端な寄りのカットは顔の類似度 0.31〜0.38 で別の人になった（顔を見つけられたのは 14 コマ中 3 コマ）。目の寄りのカットは顔の上と下に枠が 2 つ出て 2 人になった。画像 4 枚（主人公の 3 カットの静止画と vtest の 1 コマ）: 主人公の 3 枚を 1 人にまとめ、vtest の 7 人はすべて別の人（13 秒）。--no-face（体だけ）では、洗面所とカフェの静止画の体の類似度が 0.456 で、同じ人にできなかった。vtest の 25 秒（4 コマ/秒・574 秒）: 22 区間 → 12 人。10fps の追跡の番号を基準にすると、別の人を別にできた組 142/146・同じ人を同じにできた組 4/7。目で見直すと、標識の陰を出入りして基準でも分かれていた黒いコートの人を 4 区間つないだのは正しく、誤りは並んで歩く 2 人の取り違え（1 区間）と、交差した人が混ざった区間を別の人につないだ（1 区間）。同じ人なのに別のままの区間が 1 つ。OpenCV 4.14 の dnn で YouTu ReID に入れる枚数を途中で変えると出力が壊れる（値が発散し最後は NaN）ことを見つけ、1 枚ずつ通すようにした（同じ枚数なら作り直した網と完全に一致）
- 限界・注意: 同じ人かは、顔（36px 以上で見つかった時）と服装・体つきで判断する。そのため、着替えた同じ人は顔が見えないとつながらず、似た服の別人（黒い上着どうしなど）は体だけだと似る（vtest の別人で最大 0.68）。逆に、同じ服でも照明や写り方が大きく違うカットどうしは体だけでは似ないことがある（story540 の洗面所と他のカットで 0.46〜0.54。日差しとカフェは 0.76）ので、カットをまたいでつなぐには顔が見えている方がよい。顔の極端な寄りでは顔を見つけにくく、類似度も下がってつながらないことがある（story540 の顔の寄り。横顔・うつむきは試していない）。人が交差した所で追跡が入れ替わると、その区間に 2 人分が混ざって誤ってつながる。--margin で厳しさを変えられる（負の値でまとまりやすく、正の値で分かれやすい）。AI 生成の人物はカットごとに顔立ちが少し変わることがあり、正解そのものがあいまいなことがある。用途は自分の映像の中で同じ人をつなぐことに限る（実在の人の特定には使わない）。accurate の検出が重く、15 秒で約 4 分
- 確かめた素材と方法: story540.mp4（目で決めた正解と比べた。reid_story.py）、vtest.mp4 の 25 秒（10fps の追跡の番号を基準に数え、一覧を目で見た。reid_vtest.py）、vtest の 13 人の前半・後半の組（reid_calib.py）、画像 4 枚（reid_images.py）、YouTu ReID の枚数の不具合（youtu_batch.py）。すべて vfx-tests/mot/ に置いた

```bash
                          [--duration DURATION] [--max-frames MAX_FRAMES]
                          [--max-side MAX_SIDE] [--model {accurate,fast}]

                          src [src ...]
```

## 87. 異常検知（`anomalies`） ◎

- 何をする: ふだんと違う動きや画の場面を見つける
- 頼み方の例: 「長い映像の中で、いつもと違うことが起きた時刻を探して」
- 中身: コマごとに 5 つの特徴を出す: 速い動き（DIS オプティカルフローの速さの上位 5%）・画面全体の動き（フローの中央値）・明るさ・色と形（16×16 の Lab の小さな画）・内容（SigLIP 2 の特徴量、--look-step 0.25 秒ごと。--no-ai で使わない）。76 の方法で場面に分け、同じ場面の前と後ろ（各 --window 2 秒）の中央値と、その 2 つの真ん中の 3 つと比べた差のいちばん小さい物を「ずれ」とする（カットのように変わって続く物や、なだらかな変化は小さく、前後のどちらとも違う一瞬だけが大きい）。場面の端は隣の 2 コマとも比べる。ずれ ÷（1.4826 × 動画全体のずれの中央値）＝頑健な z 値が --z（8）以上のコマをつなげて区間にする。動きは log(1+速さ/0.5px) で比べる（速く動く場面の中の揺らぎより、静かな所の急な動きを重く見る）。色と形の差は色の成分ごとの画素の差の中央値（数人が歩く程度の一部の変化に鈍い）。さらに、1 秒以下の短い場面で前後の場面どうしが似ている物を「差し込み」（違いが色の全体のずれなら「明るさ」）とする

- 限界・注意: 「前後と違う一瞬」を探すので、2 秒（--window）より長く続く変化（2 秒の停止そのもの等）は異常にしない（停止は再開の飛びで見つかった）。編集済みの作品では、演出（フラッシュ・押し出しの転換・文字の動き）も異常として出る（v4 で 14 件）。人の手が画面に入る・速く動き出すなど、ふつうの出来事も「いつもと違う動き」として出る。1 秒以下の場面で前後がつながる物は「差し込み」とするので、意図した短いカットバックも出る。基準は z 8（6 では普通の映像でも出始め、12 では弱い異常を落とすおそれ）
- 確かめた素材と方法: make_anomalies.py（6 種類の異常の正解つき）と test_anomalies.py（z 6・8・12、手を加えない vtest・a-eye・b-lashlift・c-brow・story540・v4）、--fps 5・--no-ai の確認。確認画像 87-anomalies-synth.jpg・87-anomalies-story.jpg・87-anomalies-v4.jpg

## 89. 重複フレーム検出（`duplicates`） ◎

- 何をする: 同じ画が続いて止まって見える所を見つける
- 頼み方の例: 「コマが重なってカクつく所がないか調べて」
- 中身: 長辺 480px の灰色のコマで、前のコマとの差を 8×8 の区画ごとに平均し、どの区画も 5 以下かつ画面全体の平均の差が 0.3 以下（0〜255）なら同じ画とする（圧縮の乱れは広く薄く、ゆっくりした動きは平均の差が大きい）。続いた重複をまとめ、0.5 秒以上なら「停止」。前後の動きが大きい所の重複を「カクつきが目立つ」とする。重複のまとまりの間隔がそろっていれば（8 割以上が同じ間隔±1）フレームレート変換の跡として、元のコマ数 ≒ fps ×（1 − 1 回の重複の数 ÷ 間隔）を出す。--ffmpeg で ffmpeg の mpdecimate（落とすコマ）と freezedetect（止まった区間）の結果も JSON に入れて比べる。出力: JSON と確認画像（差のグラフと、前・元・重複・次のコマ）

- 何をする: 見る人の目が集まりやすい場所を推定する
- 頼み方の例: 「見る人の目が行きやすい所を色で示して」
- 中身: 学習した視線のモデルではなく、古典的な方法の組み合わせ（長辺 320px で計算）: OpenCV の spectral residual（Hou & Zhang 2007）・色の珍しさ（Cheng ほか 2011 の histogram contrast をもとに、少ない色も近い色に置き換えずに比べる）・向き（4 方向の Gabor の強さ）を、それぞれ Itti ほか 1998 の正規化 N()（山が 1 つだけ目立つ地図を強める）にかけて平均。そこに顔（YuNet。目の高さを中心に。重み 0.6）・文字（PP-OCRv3 の文字検出。顔を文字と見なすことがあるので、顔に重なる枠は除く。0.4）・動き（DIS の動きから画面全体の動きを引いた、周りと違う動き。動画のみ。0.4）を足し、画面の中央を重くする（0.3）。動画は前のコマと半々に混ぜる（カットでは混ぜない）。--method spectral / fine で OpenCV の 1 つだけも選べる。出力: 熱の色の重ね表示（山に番号。画像は元と並べた JPG、動画は MP4・一覧）、--map で白黒の地図、JSON（コマごとの山 3 つ・3×3 の区画ごとの平均と、全体の平均・いちばん目が行きにくい区画）

## 97. 代表色の抽出（`palette`） ◎

- 何をする: 場面の色合いを、数色の代表の色にまとめる
- 頼み方の例: 「この場面に使われている主な色を数色出して」
- 中身: CIELAB の k 平均（OpenCV の kmeans。k-means++・8 回試して最良・乱数の種は固定）。色の中心は「色の変化が小さい半分の画素」（Lab の 3 成分の Sobel の和が中央値以下）で求め、割合はすべての画素を最も近い中心に振り分けて数える（輪郭の中間色が 1 色として選ばれるのを防ぐ）。中心どうしの色差 CIEDE2000（Sharma ほか 2005 の式を実装）が 3 未満の色はまとめる。長辺 240px に縮めて数える。動画は 76 のカット検出で場面に分け（--every で一定間隔にも）、各区間の両端 1 割を除いた最大 12 コマを使う。動画全体の代表色は区間の長さで重みをつける。出力: 色見本の帯の PNG（区間ごとに代表のコマと割合どおりの帯、#RRGGBB と %）、JSON（#RRGGBB・RGB・Lab・割合）

## 99. フラッシュ検出（`flashes`） ○

- 何をする: 明るさが激しく点滅する区間を見つける
- 頼み方の例: 「チカチカと強く点滅する所がないか確かめて」
- 中身: WCAG 2.3.1 の考え方: コマを長辺 320px で読み、sRGB を光の強さに戻して（IEC 61966-2-1 の式）相対輝度を求め、長辺 64 個の区画で平均する。区画ごとに山と谷を追い、相対輝度 0.1 以上の上下（暗い側が 0.8 未満）を 1 回の変化、反対向きの 2 回で 1 回の点滅とする。赤は WCAG 2.0/2.1 の注 3 の式（どちらかの状態で R/(R+G+B) ≥ 0.8、(R−G−B)×320 の変化が 20 より大きい）。直前 1 秒の点滅の回数を区画ごとに数え、画面の 25%（--area）以上の面積が達した回数をその時の点滅の回数とし、3 回（--max-flashes）を超える区間を出す（面積を画面全体に対する割合で見るのは ITU-R BT.1702 の考え方）。出力: JSON（コマごとの回数・区間・判定）とグラフ画像
- 実測: 合成映像（30fps・32 秒）の 8 区間: 全画面の黒⇔白 2・3・4・8Hz → 2.0・3.0・4.0・8.0 回/秒（2・3Hz は範囲内、4・8Hz は超過）、画面の 10% だけ 8Hz → 0（範囲内）、30% だけ 8Hz → 8.0（超過）、暗い赤（sRGB 100,0,0）⇔黒 4Hz → 赤 4.0（超過。明るさは 0.5 で範囲内）、相対輝度 0.85 の灰⇔白 8Hz → 範囲内（暗い側が 0.8 以上）: 8/8 が期待どおり。超過区間は 4.13〜7.03・8.07〜11.03・16.07〜19.03 秒、赤 20.13〜23.03 秒（正解 4〜7・8〜11・16〜19・20〜23 秒）。v4（白いフラッシュ・明滅する光）: 最大 2.0 回/秒（1.43 秒、光る大きな文字「卒業」が飛ぶ所）、赤 0、既定の 25% では範囲内。--area 0.05 では 0.53〜2.57 秒が最大 4 回/秒、0.02 では 5 区間（報告のみ。広告は直していない）。速さ: v4 で 3.2 秒、story540 で 2.6 秒
- 限界・注意: 簡易な目安で、Harding FPA や PEAT のような認証用の判定ではない。面積は画面全体に対する割合で見る（WCAG の「視野 10 度のどこかの 25%」とは違う。1024×768 で見る机の画面なら、それは画面の約 2.8% の面積に当たるので、厳しく見る時は --area 0.03）。表示の明るさ（cd/m²）は考えない（相対輝度 0.1・0.8 は、表示の最大 200cd/m² なら BT.1702 の 20cd/m²・160cd/m² に当たる）。縞・格子などの模様、5 秒を超えて続く点滅の扱いは見ていない。WCAG 2.2 の注（w3c/wcag の原文で確認）は赤の点滅を「R/(R+G+B) ≥ 0.8 の状態を含み、CIE 1976 UCS の色度の差が 0.2 を超える上下」に改めているが、この道具は 2.0/2.1 の注の式のまま（黒の色度の扱いなど ISO 9241-391 を確かめられないため、2.2 の式は入れていない）
