# 1/4 動きの解析（画面の中の動きを測って読み取る）

`uv run python -m vfx <コマンド> --help` で引数の詳細が出る（tools/ で実行）。

## 1. オプティカルフロー（`optical-flow`） ◎

- 何をする: 1 画素ずつの動き（向きと速さ）を求める
- 頼み方の例: 「この映像の動きを矢印と色で見えるようにして」
- 中身: 各コマから次のコマへの、画素ごとの動き（横・縦の px）を測る。既定は OpenCV の DIS（ai.optical_flow、プリセット MEDIUM）。--method で Farneback、torchvision 0.21 の RAFT small・RAFT large も選べる。RAFT の重みはどちらも FlyingChairs と FlyingThings3D だけで学習した C_T_V2（small は ai.RaftFlow の既定。large は torchvision の既定 C_T_SKHT_V2 が KITTI（CC BY-NC-SA）でも学習しているので、C_T_V2 を指定）。torchvision は BSD-3-Clause（torchvision の説明では、学習済みの重みには学習データ由来の条件が付くことがあるとされる。既定の dis はモデルを使わない）。出力: MP4（overlay＝元の映像に色を重ねて白い矢印／color＝色だけ（色相 = 向き、明るさ = 速さ）／arrows＝向きの色の矢印。右下に色の見本の輪）、コマごとの動きの量（平均・中央値・95% 点・動いている所の割合・画面全体の中央値の動き ≒ カメラの動き。元の px）の JSON とグラフ、--save-flow で生のフロー（float16 の .npz）。色の明るさの上限は、前もって 16 組を DIS で測った 99% 点に固定（コマごとに変えるとちらつくため）。画像は --next の 2 枚の間
- 実測: 正解つきの合成の組（graf 640×480 と AI 生成の顔 540×960 × 平行移動 (7,−4)・小数の移動 (3.4,−2.7)・回転 2°＋拡大 3%・大きな移動 (−24,13)・2 つの動き）の EPE（終点の誤差の平均）: dis 0.056〜0.203px（2 つの動きの物の縁では 3.3〜3.4px）、raft 0.078〜0.183px（縁 2.7px）、raft-large 0.037〜0.081px（縁 0.59〜0.62px）、farneback 0.25〜17.8px（顔の肌と 24px の動きで崩れる）。vtest に既知のパン（最大 8.3px/コマ）を足した 72 コマ: 画面全体の中央値の動きと正解の差 平均 0.034・最大 0.067px（dis）、0.043・0.090px（farneback）、0.068・0.155px（raft、23 組）。固定カメラの vtest: 中央値の動き 0.004px 以下。速さ（540×960 の 1 組。CPU が空いている時）: dis 0.02 秒、farneback 0.09 秒、raft 1.1 秒、raft-large 2.6 秒（他の作業と CPU を分け合うと raft は 3〜5 倍遅くなった）。vtest 4 秒（768×576・40 コマ）を確認用 MP4 とグラフ込みで 3.5 秒
- 限界・注意: dis は物の縁（動きの境目）で 3px 前後ずれる（縁が大事な時は raft-large。ただし dis の約 100 倍遅い）。farneback は模様の少ない所（肌）と大きな動きに弱い。模様の無い壁などでは dis が数 px の見かけの動きを出すことがある（basketball の壁。色に出る）。カットをまたぐコマの動きには意味が無い。矢印は 4px 未満を描かない（小さな動きは色で見る）。--save-flow は 540×960 で 1 コマ約 2MB をメモリに貯めてから書く（1.5GB を超えそうな時は止まる。--max-side・--duration で小さく）
- 確かめた素材と方法: make_flow_tests.py の正解つきの画像の組 10 組 × 4 方法と、vtest に既知のパンを足した pan-vtest.mkv（test_optical_flow.py）。basketball1/2・vtest・story は目で確認

```bash
cd tools && uv run python -m vfx optical-flow [-h] [-o OUT] [--json JSON] [--start START]
                                  [--duration DURATION]
                                  [--max-frames MAX_FRAMES]
                                  [--max-side MAX_SIDE] [--next NEXT]
                                  [--method {dis,farneback,raft,raft-large}]
                                  [--view {overlay,color,arrows}]
                                  [--max-mag MAX_MAG] [--step STEP]
                                  [--arrow-scale ARROW_SCALE]
                                  [--min-mag MIN_MAG] [--save-flow]
                                  [--no-legend]
                                  src
```

## 2. モーショントラッキング（`track`） ◎

- 何をする: 動く人や物に、文字や図形を付いて行かせる
- 頼み方の例: 「歩く人の頭の上に名前の札を付いて行かせて」
- 中身: OpenCV の VitTrack（opencv_zoo の object_tracking_vittrack_2023sep.onnx。Apache-2.0）と CSRT（opencv-contrib）を並べて走らせる hybrid が既定（--tracker vit / csrt で片方だけも可）。2 つの枠が重なる（IoU 0.5 以上）時は平均、食い違う時は「直前の動きから予想した位置」と「直近 1 秒の枠の大きさ」に近い方を使い、使わなかった方は見失った時はすぐ、食い違いが 1 秒続いたら使った方の枠でやり直させる。最初の枠は --box か --auto（face = YuNet、それ以外は detectors の COCO の物体検出で大きい順の --pick 番目）。カット（色の分布の Bhattacharyya 距離と縮めた白黒の画の相関。0.25 秒以内に戻る白いフラッシュは除く）で追跡を止め、--redetect なら探し直す（同じ場面では直前の位置に近い物、カットの後は大きい順の --pick 番目）。軌跡は前後を見るガウスでならし（σ 0.1 秒、端は点対称に延ばす。大きさは 2 倍の σ）、0.5 秒までの見失いは直線でつなぐ。出力: 文字（core.draw_text）を付けた確認 MP4（音声は残す。--clean で枠と軌跡を消す）、コマごとの JSON（生の枠・ならした中心と大きさ・確からしさ・使った追跡器。元の映像の px）、HyperFrames 用の .js（window.__vfxTracks[出力の名前] に作品の fps（既定 30）の時刻つきで x・y・w・h・見えているか v。作品の大きさ（既定 1080×1920）に映像を object-fit: cover で置いた時の px。window.vfxFollow(tl, 要素, データ, {start, mediaStart, anchor, dx, dy}) が作品のコマごとに tl.set を並べる）
- 実測: 正解つきの合成映像（starry_night の上を魚（最初の枠 112×93px）がリサージュで動く。1 コマの動き 中央値 11px・最大 17px、大きさ ±25%・傾き ±12°・背景もパン。540×960・180 コマ）: hybrid の中心の誤差 平均 4.80px（最大 12.4）・IoU 0.848（vit 6.07px・0.796、csrt 5.34px・0.833）。がたつき（誤差の 2 階差分の RMS）は生 3.38px → ならし後 0.77px（ならし後の平均誤差は 5.53px。速い曲がりを少し丸める）。柱（幅 60px）が魚の 60〜73% を 2 回隠す合成映像: hybrid 8.01px（最大 29.7）・IoU 0.727・見失い 0、csrt 7.74px・0.699、vit 163px・0.144（隠れると枠が見えている所まで縮み、その後に画面いっぱいへ広がって戻らない）。顔（毎コマの YuNet の枠と比べる）: plate-stand 9.5px（顔の幅の 5.7%）・IoU 0.81、plate-laugh 5.7px（3.3%）・0.91、story 5.8〜8.8 秒 8.6px（5.2%）・0.85（vit は 8.9・8.1・6.0px、csrt は 10.4・6.8・12.2px）。vtest の人（--auto person、10 秒）: 前を別の人が横切る前（5.5 秒まで、検出をつないだ枠と比べて）4.3px・IoU 0.71、横切った後も同じ人を追った（目で確認。検出をつないだ方が別の人に移った）。カット: story を 5.8 秒から追うと本当のカットのコマ（元のコマ 213 = 8.875 秒。測った時の表示は 8.84 秒で、--start がコマの境目でない分 1/3 コマ早く出ていた。2026-11-15 に core.t_of を直し、今は最初のコマの本当の時刻から数える）で止まり、--redetect では 0.25 秒後から次の場面の顔を追った。HyperFrames 0.9.43 の作品（plate-laugh を data-start 0.5・data-media-start 0.2 で全面に置き、vfxFollow で札を付ける）で check 合格、snapshot の 0.6・0.85・1.0・1.4・1.75 秒で札の位置は .js の値と 1.0〜1.9px 差、その画で YuNet が見つけた顔の上端の中央と横に 0.2〜15px（作品の px）。素材の 0.6 秒からの追跡（--start 0.6）を付けた 2 つ目の札は、作品の 0.9 秒まで隠れ、その後は .js の値と 0.7〜0.9px 差。速さ: 540×960・180 コマで hybrid 7.1 秒・vit 3.9 秒・csrt 6.3 秒（読み込み 2 回と書き出し込み）
- 限界・注意: hybrid は vit の約 2 倍の時間。ならし（--smooth 0.1 秒）は速く曲がる動きを少し丸める（合成映像で平均 +0.7px。0 で無効）。大きく長い隠れでは見失い、0.5 秒（--max-gap）より長いと文字を消す。--redetect は --auto の時だけ。人が交差すると別の人に移ることがある（vtest の交差 1 回では移らなかった）。カットの見分けは強い照明の変化で誤るかもしれない（試していない）。.js は映像を作品の画面いっぱいに cover で置く前提（違う置き方なら JSON の元の映像の px から換算する）
- 確かめた素材と方法: make_track_synth.py の合成映像 2 本（遮り無し・柱で遮る）を eval_track_synth.py で正解と比べた。plate-stand・plate-laugh・story540 の顔と vtest の人を eval_track_real.py で検出と比べ、確認画像で交差・カットを目で見た。hf_check.py で HyperFrames の作品の snapshot から札の位置を測った

```bash
cd tools && uv run python -m vfx track [-h] [-o OUT] [--json JSON] [--start START]
                           [--duration DURATION] [--max-frames MAX_FRAMES]
                           [--max-side MAX_SIDE] [--box BOX] [--auto AUTO]
                           [--pick PICK] [--tracker {hybrid,vit,csrt}]
                           [--redetect] [--text TEXT]
                           [--text-pos {above,below,center}]
                           [--text-size TEXT_SIZE] [--smooth SMOOTH]
                           [--max-gap MAX_GAP] [--clean] [--fps FPS]
                           [--comp-size COMP_SIZE]
                           src
```

## 3. 手ぶれ補正（`stabilize`） ◎

- 何をする: 手持ちの揺れを抑えて、画面を落ち着かせる
- 頼み方の例: 「手持ちで撮ったこの映像の揺れを止めて」
- 中身: 隣り合うコマの画面全体の動き（相似変換: 移動・回転・拡大）を、4×4 の升目ごとに選んだ特徴点（計 480 点）を往復で確かめる Lucas-Kanade（ai.track_points）で追って RANSAC で求め、つないでカメラの通り道にする（画面の中心が原点）。人物と背景が別々に動く時は、前の組で選んだ層の点を引き継いで同じ層を選び続ける。人物の判定（MediaPipe の selfie。Apache-2.0）が場面を通して安定している場面だけ、人物を除いた背景で測り直す（2 回読む）。往復で追える点がほぼ 0 の所（カット・白いフラッシュ）で通り道を切る。既定の l1 は通り道を L1 最適化でならす（Grundmann ら 2011 の考え方を、横・縦・回転・拡大の数値ごとに scipy の HiGHS で解く。1〜3 階の差の重み 1・1・100、生の道から離れる重み 1、余白は画面の ±6%・回転 ±2 度・拡大 ±5%。端は 1 秒ぶん直線の延長で延ばして解く）→ 止まる・等速・なめらかな加減速の区間に分かれる。全コマの四隅が元の絵で埋まる最小の拡大率（全コマ共通、上限 1.25 倍）を計算で求めて端の黒を隠し、明るさだけ軽く締める（unsharp 0.6）。--method gauss（前後 0.5 秒のガウス）、--method vidstab（ffmpeg の vidstabdetect・vidstabtransform。mincontrast 0.1・optalgo gauss・optzoom 1・bicubic）、--tripod（完全に止める）も使える。出力: MP4（音声は残す）・JSON（揺れの前後・拡大率・切れ目）・確認画像（約 1 秒ぶんのコマの平均の前後・前後のコマ・コマ間の動きのグラフ）。scipy・matplotlib は他の依存関係（easyocr・mediapipe など）が入れている物を使う
- 実測: 正解つきの試験（揺らす前の映像に既知の揺れ（1.5〜6 Hz、各軸 5〜6px・回転 0.4 度）を加えて補正し、各コマを元のコマに SIFT で合わせて、位置の細かい揺れの残りを測る。測り方は、揺れた映像そのものを測って 8.15/7.46/7.48px（正解 8.16/7.46/7.49px）と確かめた）: 固定カメラで人が歩く vtest（768×576・80 コマ）8.16→0.03px（100% 減）、洗面所で髪を結ぶ人（540×960・64 コマ）7.46→0.22px（97% 減）、寄りながら髪がなびく人（70 コマ）7.49→0.71px（90% 減）。回転の残り 0.002・0.025・0.053 度。拡大 1.060・1.087・1.082 倍、補正で端に黒が出たコマ 0。ほかの方法: gauss 82・90・88% 減、vidstab 83・72・82% 減（vidstab は髪を結ぶ場面で回転が 0.42→0.25 度しか減らない）。人物を除かずに測ると（--with-people）髪を結ぶ場面 1.60px・寄りの場面 2.19px（人物の動きまで消してしまう）。--tripod は固定カメラの vtest を元の画角に 0.16px で止めた。AI の広告 story540（15 秒・361 コマ）: カット 4 か所を 73・139・213・297 コマ目（3.042・5.792・8.875・12.375 秒）でコマ単位で正しく切り、コマ間の揺れ 0.44→0.25px/コマ（拡大 1.034 倍。204 コマを背景で測り直した）。目・まつげ・眉の大写し（a-eye・b-lashlift・c-brow）でも 75・65・86% 減（拡大 1.01 倍）。速さ: 540×960・64〜70 コマで 6 秒前後、768×576・80 コマで 7.1 秒、story540 で 17.9 秒（他の作業と CPU を分け合った状態の壁時計）
- 限界・注意: 画面全体を 1 つの動き（相似変換）として直すので、手前と奥の視差が大きい場面や、画面の大部分が別々に動く場面では残りが出る（寄りながら人が動く場面で 0.71px）。補正の分だけ画角が狭くなる（拡大 1.01〜1.09 倍）。l1 は余白（--margin、既定 ±6%）を超える大きな揺れを残す。0.5 Hz より遅い揺れは意図した動きと区別できずに残る。目や顔の大写しのように人物の判定がコマごとに乱れる場面は、人物を除かずに測る（自動）。最初の版は人物の印をコマごとに使い分けて、まつげの施術の大写しで揺れを増やした（0.50→0.99px/コマ）ので、場面ごとに決めるように直した。手や道具が画面の大部分で動く大写しでは、その動きに引かれることがある。JSON とグラフの「後」の揺れは同じ方法で測った目安で、大写しの場面の初めなどで数コマ乱れることがある（story540 の 0〜0.2 秒の山は SIFT で測り直し、出力が揺れていないことを確かめた）。vidstab はカットで区切らない。ローリングシャッターのゆがみ（ぐにゃぐにゃ）は直らないので先に 11 を使う。白いフラッシュの各コマは切れ目として扱う
- 確かめた素材と方法: make_shaky.py（vtest と story540 の洗面所・日差しの場面に既知の揺れ）・test_stabilize.py（3 方法を SIFT の位置合わせで正解と比べる）、explore_cuts.py（カットの判定: story540 の 4 か所と、カットの無い 9 本の追える点の割合）、tune_smooth.py・tune_l1.py・tune_vidstab.py（設定の比較）、check_layers.py・check_blash.py（層の選び方・大写し）。実際の映像 story540・a-eye・b-lashlift・c-brow・v4（範囲・縮小・音声）の確認画像を目で確認

```bash
cd tools && uv run python -m vfx stabilize [-h] [-o OUT] [--json JSON] [--start START]
                               [--duration DURATION] [--max-frames MAX_FRAMES]
                               [--max-side MAX_SIDE]
                               [--method {l1,gauss,vidstab}] [--smooth SMOOTH]
                               [--margin MARGIN] [--max-zoom MAX_ZOOM]
                               [--shakiness SHAKINESS] [--tripod]
                               [--sharpen SHARPEN] [--with-people]
                               src
```

## 6. 平面トラッキング（`planar-track`） ◎

- 何をする: 平らな面を追い、そこへ別の絵をはめ込む
- 頼み方の例: 「壁のポスターの所に別の画像を貼り、動きに合わせて」
- 中身: --ref（平面を正面から写した写真）: SIFT（4000 点）＋FLANN（比 0.75）＋USAC_MAGSAC のホモグラフィーで最初のコマ（と見失った時・--every コマごと）に面を探す。--corners: 最初のコマの四隅を渡す。追跡は面の中の Shi-Tomasi の点（最大 600）を手本に、毎コマ (1) 予想: 前のコマから LK（往復の確かめつき）＋RANSAC、(2) 補正 2 回: 予想で今のコマを手本の見え方に戻し、面の中の明るさの平均と散らばりを合わせてから手本の点を LK で照らし RANSAC（1px）で残りのずれを直す。最初のコマと照らせる点が 10% を下回ったら（寄り・向きが大きく変わった時）0.5 秒ごとに取り替える「近ごろのコマ」の手本で補正する。はめ込み: 画像か動画（短ければ繰り返す。透過つき PNG・WebM 可）を四隅に透視変換し、縁を内側に --feather px ぼかす。JSON: コマごとの四隅（元の映像の px）とホモグラフィー（写真の px か最初のコマの px → そのコマ）。画像 1 枚にも使える（--ref で写真の面を探してはめ込む）。外部のモデルは使わない
- 実測: 正解つきの合成映像（graf1 の板 400×320 を針穴カメラで首振り ±30°・上下 ±15°・傾き ±8°・距離 900〜1500 で動かし、背景もパン。540×960・150 コマ）: 四隅の誤差 --corners 平均 0.06px（最大 0.16）、--ref（graf1.png 800×640）0.22px（最大 0.36）。幅 70px の棒が横切り明るさ 0.75〜1.2 倍・ぼけ σ0.8 の映像: --corners 0.18px（最大 1.44。隠れている間 0.40）、--ref 0.32px（最大 2.23）。--max-side 480（270×480 で処理）でも JSON は元の px で 0.45px・0.65px（座標の換算を確認）。実際の映像（AI 生成の広告の洗面所、鏡の下の大理石の壁。カメラが上を向きつつ 1.1 倍に寄る 62 コマ）: 62 コマすべて追えて、最初のコマの形に戻した時の面の中の残りの動き（DIS のフロー）平均 0.79px（最大 2.89）、追わない時は 29.1px。box_in_scene.png で box.png を探すと、合った特徴 74、四隅は別の方法（AKAZE＋RANSAC）の答えと平均 0.7px（最大 0.93）差。透過 PNG と動画のはめ込みも目で確認。速さ: 540×960・150 コマ（はめ込みつき）で 11〜13 秒、270×480 で処理すると 5.3 秒（他の作業と CPU を分け合った状態）
- 限界・注意: 手前の物の隠れは考えない（はめ込んだ物が手前の物の上に出る。box_in_scene では手前の箱の角に掛かった。切り抜き 51〜75 と組み合わせる）。無地の面は追えない（点が 8 未満ならエラー）。曲がった面は 25（mesh-warp）を使う。写真（--ref）と映像の見え方（照明・向き）が大きく違うと SIFT で見つからないことがある。最初のコマと照らせなくなって近ごろの手本に切り替えると、わずかなずれが残る。はめ込む物の明るさは場面に合わせない。面の大半が画面の外に出ると見失う

## 11. ローリングシャッター補正（`rolling-shutter`） ○

- 何をする: 速く振った時に斜めにゆがむ映り方を直す
- 頼み方の例: 「素早く横に振った所で建物が斜めに傾くのを直して」
- 中身: 近似。隣のコマとの画面全体の動き（03 と同じ測り方）から、各コマの撮影時点の速さ（前後の組の動きの平均。移動・回転・拡大）を出し、行ごとの撮影時刻のずれ τ = 読み出し × (行 − 中央) / 高さ（1 コマの時間に対する割合）だけ中身が動いた位置から cv2.remap で読み直す（中央の行の時刻にそろえる。縦の動きでは τ が読む行で変わるので 3 回くり返して合わせる）。--scan right/left で列ごと（横長のセンサーを縦に構えた縦動画）。--readout auto（既定）は、隣のコマとの 6 自由度のアフィンのせん断・伸び縮みと、速さの変化（加速）の関係から、読み出し時間と向きを最小二乗で推定する（当てはまり R² 0.3 未満・加速 0.5px/コマ² 未満・推定 1.5 超なら補正しない）。画像 1 枚は、縦（左右に読む時は横）に近い線分（OpenCV の LSD）の傾きを長さで重み付けした中央値から斜めのずれ（せん断）を求めて戻す。出力: MP4（音声は残す）・JSON（読み出し・向き・推定の当てはまり・コマごとの速さとずれ）・確認画像（補正の大きいコマの前後。まっすぐか見やすい補助線つき）
- 実測: 正解つきの試験（building.jpg を 2.5 倍にした縦の線の多い絵を、行ごとに時刻をずらして撮った合成映像。同じ時刻に全部の行を撮った映像が正解）: 右へ 40px/コマの速いパン（読み出し 0.8・640×480）を --readout 0.8 で直すと PSNR 20.45→39.09dB、縦の線の傾きの正解との差 3.74→0.08 度（auto は「揺れが小さく推定できない」として補正しない）。ゆっくりした揺れ（0.5〜1.5 Hz、15px）＋パン（読み出し 0.7）: auto が 0.709 と推定（R² 0.997）、PSNR 29.73→38.73dB、傾きの差 1.03→0.11 度。速い手の揺れ（2〜8 Hz、6px、読み出し 0.7）: auto 1.19（実効の値。R² 0.95）で PSNR 28.98→32.54dB（正解の 0.7 を手で与えると 32.94dB）、傾きの差 0.90→0.51 度。縦動画（列ごと、読み出し 0.6）: 向き right を正しく推定（1.01）、PSNR 29.47→33.50dB。ローリングシャッターの無い 5 本（固定カメラの vtest、揺れだけの合成 3 本、AI の広告 story540）はどれも補正しなかった（R² 0.007〜0.03）。画像: せん断 +3.0・−1.5 度を測った値と正解の差 0.02・0.01 度、直した後の傾き 0.00・0.04 度。速さ: 640×480・72 コマで 4.0 秒
- 限界・注意: 画面全体が 1 つの動きをする前提の近似。本格的な方法（ジャイロの記録を使う、行ごとの動きを連続した曲線として最適化する）と違い、手前の人物だけが速く動く・視差が大きい場面のゆがみは直らない。1 コマを撮る間に速さが変わる速い揺れ（ぐにゃぐにゃ、およそ 4 Hz 以上）は一部しか直らない（速い揺れの試験で PSNR +3.6dB、線の傾きの差は約半分）。揺れ（速さの変化）の無い等速のパンでは読み出し時間を推定できないので --readout で指定する（スマートフォンでおよそ 0.3〜0.9）。auto の値はこの補正と組の実効の値で、速い揺れでは実際より大きく出る（0.7 → 1.19、0.6 → 1.01。速さの求め方が速い揺れで小さく出る分とつり合う）。補正で読み取り位置を動かした分、画面の端は端の画素をのばして埋める（最大のずれは JSON の max_shift_px）。レンズのゆがみは考えない。画像 1 枚では、建物の縦の線がもともと傾いている分（あおりなど）も一緒にまっすぐにする。AI の生成映像にはふつうローリングシャッターは無い（story540 では補正しなかった）
- 確かめた素材と方法: make_rs.py（等速の速いパン・速い揺れ・ゆっくりした揺れ・縦動画の 4 種と、正解のグローバルシャッター）、test_rs.py（推定値・PSNR・線の傾き、ローリングシャッターの無い 5 本、画像のせん断 2 種）、確認画像を目で確認

```bash
                                     [--start START] [--duration DURATION]
                                     [--max-frames MAX_FRAMES]
```

## 13. 動き補償（`motion-compensate`） ◎

- 何をする: 動いた分をずらしてから、前後のコマを重ねる
- 頼み方の例: 「前後のコマを動きに合わせて重ね、違いを見やすくして」
- 中身: 画面全体の動き（--model: homography（既定）・affine・similarity・translation）を、前のコマの特徴点（goodFeaturesToTrack）を LK で追い（往復で確かめる。ai.track_points）、RANSAC で当てはめて求める。align: 変換をつないで最初のコマ（--start の位置）に写し、さらに最初のコマの特徴点と直接合わせ直す（つなぎの誤差がたまらない）。average: 前後 N コマ（既定 5）を今のコマに写し、はみ出した所を除いて平均（--stat median で中央値）。diff: 前のコマを今のコマに写してから差を取る（しきい値 25。はみ出した所は除く）。画像 2 枚（--next）: SIFT の対応＋RANSAC で 2 枚目を 1 枚目に写す。JSON にコマごとの変換（元の px の 3×3）・合った点の数・ずれ・カメラの動きの目安、diff では補償なしの変化の割合も
- 実測: vtest（固定カメラ）から既知の軌跡で切り出した 72 コマ（640×480。±50・±30px のパン、さらに ±2.5° の回転と ±5% の拡大）: align の 4 隅のずれ（正解の変換との差）は平均 0.03〜0.13・最大 0.39px（カメラの動きは 4 隅で最大 77px。translation 0.032、similarity 0.044〜0.045、affine 0.051〜0.052、homography 0.115〜0.126）。diff: 動く人の正解（元の固定カメラの差）に対し 精度 100%・再現率 98.9%（回転・拡大つきも同じ）。補償なしの差（16）は精度 19.2%（背景の輪郭も出る）で、変化の割合は 12.5% → 1.9% に減った。average（σ12 のノイズ・5 コマ）: PSNR 26.6 → 34.2dB（mean）・34.1dB（median）。合わせずに 5 コマ平均すると 23.7dB（ぼける）。graf1 を既知のホモグラフィーで写した画像: 4 隅のずれ 平均 0.32・最大 0.54px（SIFT の対応 1619 点）。固定カメラの vtest を align: 4 隅の動き 平均 0.07px。速さ: 640×480・72 コマの align が約 3.7 秒
- 限界・注意: 画面全体を 1 つの平面の動きとみなす。奥行きの差が大きい場面（手前の柱と奥の部屋。story 6〜7.5 秒）では合わせきれず、diff の変化が減らない（9.9% → 9.9%）・align で画がゆがむ。動く物が画面の大半を占めると背景を取り違える。align は最初のコマから離れるほど端が黒くなる（切り抜かない）。カットをまたぐと合わない（動きなしとして扱い、JSON の failed に数える）。動きの種類が分かっている時は、少ない自由度（translation・similarity）の方が正確（上の数値）。ECC（画素の明るさの相関）で詰める方法も試したが、合成のパンで 4 隅のずれが平均 0.87〜1.13px と特徴点だけ（0.12px 前後）より悪かったので入れていない（歩く人に引っ張られる）
- 確かめた素材と方法: test_motion_compensate.py: vtest に既知のパン・回転・拡大を足した映像（正解の変換・正解の動く人・ノイズなしの映像と比べる）、graf1 を既知のホモグラフィーで写した画像。graf1/graf3・vtest・story は目で確認

```bash
cd tools && uv run python -m vfx motion-compensate [-h] [-o OUT] [--json JSON]
                                       [--start START] [--duration DURATION]
                                       [--max-frames MAX_FRAMES]
                                       [--max-side MAX_SIDE] [--next NEXT]
                                       [--mode {align,average,diff}]
                                       [--model {homography,affine,similarity,translation}]
                                       [--frames FRAMES]
                                       [--stat {mean,median}] [--gap GAP]
                                       [--threshold THRESHOLD] [--blur BLUR]
                                       [--view {heat,mask}] [--no-legend]
                                       src
```

- 中身: 人の検出は共有の detectors（accurate: torchvision〔BSD-3-Clause〕の Faster R-CNN v2 / fast: MediaPipe の EfficientDet-Lite2〔Apache-2.0〕。どちらも COCO の 80 種類で、--classes で車なども追える）。追跡は ByteTrack と同じ考え方を自作: 等速のカルマンフィルター（枠の中心・縦横比・高さと速さ）で次の位置を予測し、ハンガリアン法（scipy）で IoU を照合する。1 段目は確信度 0.5 以上の検出を追跡中・見失い中の人へ、2 段目は 0.1〜0.5 の検出（隠れかけた人）を残った追跡中の人へ結ぶ。新しい番号は 0.6 以上の検出から始め、次のコマでも結べたら確定。見失っても --keep 秒は同じ番号で待つ。カットの変わり目（縮小したコマの HSV の差が 27 以上）では追跡をやり直す。出力: 番号つきの枠と足元の軌跡を描いた MP4、番号ごとの時刻と枠（元の大きさの px）の JSON、12 コマを並べた確認画像
- 実測: 追跡だけの試験（正解の枠に 2px のゆらぎ・見落とし 10%・誤検出 5%・重なると確信度が下がる、6 人・200 コマ・10 通りの平均）: IDF1 0.847・MOTA 0.801・入れ替わり 1.3 回・番号 7.0 個（正解 6 人）。重なりで確信度が下がらない場合は IDF1 0.942・入れ替わり 0 回・番号 6.0 個。検出から通した合成映像（同じ服の AI 生成の人物 4 人が交差し、手前の人が奥の人を隠す。768×576・10fps・120 コマ）: accurate で MOTA 0.895・IDF1 0.772・見落とし 33/382・誤検出 5・番号 4 個（正解 4 人）・入れ替わり 1 組（2 人が交差して番号を取り違えた）。入れ子の枠を除かない（--nested 1.1）と MOTA 0.929・IDF1 0.776・見落とし 18・番号 6 個（短い余分な番号が出る）。fast は MOTA 0.775・IDF1 0.610・入れ替わり 5 回。vtest（実写の固定カメラ、0〜25 秒・250 コマ。入れ子の除去を入れる前の版）: accurate で番号 20 個、fast で 17 個。標識のそばで 3 人が重なった所（1.5〜4.2 秒）を拡大して見ると、標識に隠れた人が 3→6→3、黒いコートの人が 2→6 に入れ替わり、黒い上着の人は 1 のままだった。story540（AI 生成の広告、6 コマ/秒）ではカットごとに 1 人に 1 つの番号（洗面所・日差し・顔の寄り・カフェで番号 3〜6）で、同じ人に 2 つの番号が付くことは無かった（目の寄りのカットだけ、顔の上下に 2 つの枠と番号）。カットの変わり目: story540 で 3.042・5.792・8.875・12.375 秒（正解 3.0・5.79・8.88・12.38 秒。1 コマ以内）、固定カメラの vtest では誤りなし（差の最大 4.6）。速さ: accurate は 1 コマ約 2〜2.5 秒（CPU が空いている時）、他の作業と分け合った状態では 4.8 秒（768×576）〜15 秒（540×960）。fast は 1 コマ 0.13 秒
- 限界・注意: 見た目の特徴を使わず、位置と動きだけで結ぶ（ByteTrack と同じ）。そのため、似た服の人が重なって隠れたり、体の一部だけが見えて枠の形が変わったりすると、番号が入れ替わる・新しい番号になることがある。本格的な追跡（BoT-SORT・StrongSORT など）が使う、見た目の特徴での照合とカメラの動きの補正は入れていない。カメラが速く動くと IoU が合わず番号が切れやすいはず（試していない）。カットの変わり目では番号を付け直すので、別のカットや長く隠れた後の同じ人をつなぐのは 85（reid）を使う。同じ人の頭だけの枠などを除く処理（--nested）は、重なって隠れた人も除くことがある。accurate は遅いので、長い映像は --fps 10 などに下げるか --model fast（小さい人・重なった人を見落としやすい）

## 23. シーンフロー（`scene-flow`） ○

- 何をする: 奥行きの方向も含めて、動きを求める
- 頼み方の例: 「近づいてくる物と遠ざかる物が分かるように動きを出して」
- 中身: 2D のフロー（DIS。--flow で farneback・raft）から、物が 1 コマで何倍に大きく見えたか（局所の拡大率 s）を求め、奥行き方向の動き（s > 1 は近づく。距離は約 1/s 倍になる）とする（optical expansion の考え方）。細かい尺度（σ2px）でフローを微分して画素ごとに s = √det(I + J) を出し、行き帰りのフローが合わない所（隠れる所）と動きの境目（微分が大きい所）を除いてから σ（短い辺の 1/30）でならす（境目をまたいでならすと、近づく物のまわりに「遠ざかる」輪ができた）。--fov の画角で 3D の動き（距離に対する割合 ΔX/Z・ΔY/Z・ΔZ/Z）も .npz に出す。--method depth は Depth Anything V2 Small（Apache-2.0。ai.DepthEstimator のモデルの生の出力）の逆深度をフローに沿って前後のコマで比べる方法（比べる用）。出力: 近づく所を赤・遠ざかる所を青で塗り、白い矢印で横の動きを描いた MP4、コマごとの近づく・遠ざかる所の割合・画面全体の拡大（カメラが寄る・引く）・ぶつかるまでの秒数の目安の JSON とグラフ。画像は --next の 2 枚の間
- 実測: 画面全体が 1 コマ 1.5% 大きく／小さくなる合成映像（長辺 480 で解析）: 画面全体 +1.450%／−1.408%（正解 +1.5／−1.48%。長辺 960 では +1.492%）、画素ごとの誤差の中央値 0.12〜0.17%、近づく・遠ざかるの見分け 99.6%／99.9%。止まった背景の上で板が 1 コマ 2% 大きく・小さくなる合成映像（640×480）: 板の値の誤差 平均 0.09〜0.12・最大 0.4%、見分けの正しさ 左 100%・右 100%・背景 99.1%。2 枚の画像（回転 2°＋拡大 3%）: +2.96%。depth 方式は画面全体の拡大を 0 とみなし（+0.007%）、板の見分けも 55〜59%（背景 18%）と不正確で、4〜36 倍遅い。実写 story（人がカメラへ歩いてくる 2.9 秒。AI 生成）: 顔の枠（YuNet）の大きさは ×1.32（+0.44%/コマ）、顔の枠の中の値を積み上げると ×1.42〜1.43（+0.55%/コマ）。近づく向きは合い、速さは約 1.25 倍に出た（コマごとの値は顔の枠の揺れが大きく比べられない）。固定カメラの vtest の止まった背景で近づく・遠ざかるとした画素 0.32%。速さ: 640×480・36 コマで約 7 秒（DIS を行き帰り 2 回）
- 限界・注意: 単眼の近似。「大きく見える割合」から求めるので、物の向きが変わる・形が変わる動き（腕・脚・口・髪・服）にも色が付き、実写では斑になる。遠くの小さな歩く人（vtest）は 1 コマ 0.5% 前後しか大きさが変わらず手足の動きに埋もれる（人ごとの向きの一致 46〜49% ＝ 当て推量と同じ）。3D の動きは距離に対する割合で、実際の速さ（m/秒）は分からない（--fov は仮の画角）。動きの境目・隠れる所には色を塗らない。depth 方式は Depth Anything の出力がコマごとに倍率が決まらないので画面全体の中央値でそろえる（そのため画面全体の近づきは測れない）

## 24. ブロックマッチング（`block-match`） ◎

- 何をする: 画面を小さな升に分け、升ごとの移動を探す
- 頼み方の例: 「画面を区切って、区切りごとにどれだけ動いたかを出して」
- 中身: 16×16（--block）の区画ごとに、前のコマの ±16px（--range）をすべて探し、差の絶対値の和（SAD）が最小の所を選ぶ（自前の全探索。ずれごとに画面全体の差を取り、区画ごとに平均。差が同じなら小さいずれ）。隣のずれの SAD から「等角直線」の当てはめで 1px より細かく求める（--no-subpixel で 1px 単位）。--search で ffmpeg の mestimate（PyAV のフィルター経由。esa＝全探索・tss・tdls・ntss・fss・ds・hexbs・epzs・umh。1px 単位）も選べる。模様の少ない区画（明るさの標準偏差 3 未満）は除く。出力: 区画ごとの矢印（--view color で区画を動きの色で塗る）の MP4、コマごとの要約（最も多い動き・平均・動いている区画の割合・一致の悪さ）の JSON、--save-vectors で区画ごとの動きの .npz。画像は --next の 2 枚で、JSON に全区画の動き
- 実測: 正解つきの画像の組（graf 640×480・AI 生成の顔 540×960）: 平行移動 (7,−4) と 2 つの動き（板 (−9,5)・背景 (3,1)）は full・esa・umh で 100%、epzs で 99.9〜100% の区画が正しい（誤差 0.5px 未満）。tss 52〜64%・ds 61〜93%・hexbs 45〜62%（局所の谷に落ちる）。(−24,13) は ±16 では 0%、--range 32 で 100%。小数 (3.4,−2.7): 誤差 0.5px 未満が 72.6〜80.6%（1px 単位だけだと 35〜55%）、成分ごとの誤差の中央値 0.11〜0.17px、1.5px を超える外れ 2.5〜4.8%。回転 2°＋拡大 3%（探す範囲に入る区画）: 83〜86%・平均誤差 0.34〜0.37px（1px 単位では 64%）、--range 32 で全区画 83〜87%。実写 vtest の 2 コマ: 自前の全探索（1px 単位）と ffmpeg esa の答えが模様のある 1591 区画で 100% 一致。速さ（540×960・16×16・±16）: full 0.37〜0.41 秒/コマ、esa 0.27〜0.28、epzs 0.007、ds 0.014〜0.015、hexbs 0.009〜0.010。story で測った平均の速さは full 9.3・epzs 8.7・ds 7.4・hexbs 5.8px/コマ（速い探し方は大きな動きを小さく見積もる）
- 限界・注意: 区画の中は 1 つの平行移動とみなすので、回転・拡大・物の縁をまたぐ区画は不正確。探す範囲より速い動きは測れない（--range を上げると時間は (2×範囲+1)² に比例）。小数のずれは、まっすぐな縁や模様の少ない区画で 1px 以上外れることがある（開口問題）。速い探し方（tss・ds・hexbs）は大きな動きで局所の谷に落ちる。細かい動きの地図が欲しい時は 01 optical-flow
- 確かめた素材と方法: test_block_match.py: 正解つきの画像の組 10 組を 8 通りの探し方で、--range 32、vtest の実写で ffmpeg esa と答え合わせ、story で速さ。vtest・story は目で確認

```bash
cd tools && uv run python -m vfx block-match [-h] [-o OUT] [--json JSON] [--start START]
                                 [--duration DURATION]
                                 [--max-frames MAX_FRAMES]
                                 [--max-side MAX_SIDE] [--next NEXT]
                                 [--block BLOCK] [--range PX]
                                 [--search {full,esa,tss,tdls,ntss,fss,ds,hexbs,epzs,umh}]
                                 [--no-subpixel] [--flat FLAT]
                                 [--view {arrows,color}]
                                 [--arrow-scale ARROW_SCALE] [--save-vectors]
                                 [--no-legend]
                                 src
```

## 25. メッシュワープ（`mesh-warp`） ◎

- 何をする: 格子を変形させて、貼った絵を動きや形に沿わせる
- 頼み方の例: 「顔の動きに沿うように、貼った絵を変形させて付けて」
- 中身: grid（既定）: --box（省略時は画面全体）を升目（既定 約 32px）に分けた網目を、1 升ずつ外まで広げて張る。網目の中の Shi-Tomasi の点（最大 2000）を手本に、毎コマ (1) 予想: 前のコマから LK で追った点で網目を解く、(2) 補正 2 回: 網目で今のコマを最初のコマの形に戻し（三角形ごとのアフィン）、明るさをならして手本の点を LK で照らし（往復 1.5px 未満、6px より大きいずれは繰り返し模様の取り違えとして捨てる）、網目を解き直す。網目は頂点の最小二乗（点の重心座標の式＋網目の線に沿った 2 階差分のなめらかさ（アフィンの動きはゆがめない。--stiff）＋弱い引き寄せ。Huber の重みで外れた点を弱める）。カットで止める。face: MediaPipe FaceLandmarker（Apache-2.0）の 478 点のうち網目の 468 点と 852 個の三角形（目と口の中は穴）を使い、最初のコマの点を休みの形にする。貼る位置は --box か --place（頬・額・鼻・あご）と --size（顔の幅に対する割合）。点は場面ごとに時間方向にならす（σ 0.04 秒、カットで区切る）。奥の三角形から描き、向こうを向いた三角形・最初のコマで横向きだった三角形（向きの cos 0.2 未満）・そのコマで面積が全体の 3 倍を超えて伸びた三角形は描かない。貼り方: 今の網目を三角形の番号の画に塗り、三角形ごとの逆のアフィンで貼る物を引く（cv2.remap）。--blend multiply で肌の陰影を残す。出力: MP4（音声は残す）と JSON（grid は毎コマの頂点、face は毎コマの 468 点と貼った物の四隅・中心）。face は画像 1 枚にも貼れる
- 実測: grid: 正弦波でゆがめたチェッカーボード（振幅 0→18→0px・波長 260/300px、全体も ±30/±40px 動く。540×960・120 コマ。貼る範囲 400×640、網目 12×20 を 14×22 に広げて張る）に starry_night を貼り、範囲の中の点（8px おき）を正解と比べた誤差: 平均 0.21px・最悪のコマの平均 0.44px・99% 0.97px・最大 2.7px。模様を重ねて明るさが 0.8〜1.15 倍に揺れる映像: 平均 0.25px・99% 0.98px・最大 10.2px（範囲の右上の角。この角は 120 コマ中 56 コマで 3px を超えた）。最初の版（網目を貼る範囲だけに張り、補正のずれの上限なし）は 0.76px で、角の頂点が繰り返し模様で 1〜2 升ずれた（最大 88px）。6px を超えるずれを捨て、網目を 1 升外まで広げて上の値になった。face: plate-laugh の顔を既知の動き（回転 ±12°・拡大 ±15%・移動 ±40/±60px）で動かした 90 コマで、シールの中の点の誤差 平均 0.78px（最悪のコマ 1.60）、時間方向にならさないと 0.81px（2.47）。シールの中心の揺れ（2 階差分）は 0.25px（ならし無し 0.86）、実際に笑って動く plate-laugh では 0.44px（ならし無し 2.57）。plate-stand・plate-laugh の頬のハート、story の顔の寄り（8.9〜12.3 秒）の額の模様（乗算）が顔の動きに沿うことを目で確認。story のカット 5.79・8.88 秒を見分けた。速さ: grid は 540×960・120 コマで 59〜135 秒（他の作業と CPU を分け合った状態）、face は 45 コマで 2.1 秒・90 コマで 3.5 秒
- 限界・注意: grid: 模様の無い所は網目を決められない（周りからなめらかにつなぐだけ）。網目の外周（貼る範囲の外の 1 升）は暴れることがあり、貼る範囲の角は中ほどよりずれやすい（mesh-b の右上の角で最大 10px）。手前を横切る物の隠れは考えない。予想から 6px を超えて外れる動きは補正で捨てられ、追いつけないことがある。三角形ごとのアフィンなので升目より細かいゆがみは表せない（試験の波では、頂点を正解の位置に置いても網目の中で平均 0.83px ずれる。点に合わせて解いた網目の方が小さかった。升目を細かくすると減る）。速くはない（1 コマ 0.5〜1.1 秒）。face: 貼る物は最初のコマの見え方の上に置くので、最初のコマで斜めに見えていた所（頬の外側・鼻の横など）に掛かった部分は欠けたり縮んだりする（正面を向いたコマを最初にし、--place で頬の中ほどに置くとよい）。目と口の中は穴なので貼れない。手や髪の隠れは考えない。横顔など MediaPipe が顔を見つけられないコマは貼らない。顔は 1 つ（最初は大きい顔、その後は近い顔）。カットの後も、顔の同じ点の番号の所に貼り続ける
- 確かめた素材と方法: make_mesh_synth.py の合成映像 2 本を eval_mesh.py で正解と比べた（試し: try_mesh*.py で升目の数・硬さ・手本の点の選び方を比べた）。eval_face_mesh.py で既知の動きの合成映像の誤差と、plate-laugh の揺れを測った。plate-laugh・plate-stand・story540 の顔でシールと模様を貼り、確認画像で目で見た

```bash
cd tools && uv run python -m vfx mesh-warp [-h] [-o OUT] [--json JSON] [--start START]
                               [--duration DURATION] [--max-frames MAX_FRAMES]
                               [--max-side MAX_SIDE] [--mode {grid,face}]
                               [--overlay OVERLAY] [--box BOX] [--grid GRID]
                               [--stiff STIFF]
                               [--place {cheek-left,cheek-right,forehead,nose,chin}]
                               [--size SIZE] [--temporal TEMPORAL]
                               [--blend {normal,multiply}] [--opacity OPACITY]
                               [--show-mesh]
                               src
```
